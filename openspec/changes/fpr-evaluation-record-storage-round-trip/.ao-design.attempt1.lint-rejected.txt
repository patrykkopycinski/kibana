# Design

## Approach

The change proves one thing — that a `WorkerEvaluationRecord` can be written through the real `@kbn/evals` storage write path and read back through the real production-facing query path, with field fidelity and exactly-one-record-per-run semantics — by reusing substrate that is already present, mature, and deterministically tested, not by standing up any new storage. The write path is `EvalsClient.ingestScores` → `POST /internal/evals/scores` → `EvaluationScoreService.write`, which `client.create()`s `EvaluationScoreDocument`s into the `.evaluation-scores` data stream with `refresh: 'wait_for'` (`x-pack/platform/plugins/shared/evals/server/storage/evaluation_score_service.ts:109-120`). The read path is `EvalsClient.getExperimentScores` → `GET /internal/evals/experiments/{id}/scores`, whose route handler runs `buildExperimentFilterQuery` and returns the raw `_source` of each hit (`x-pack/platform/plugins/shared/evals/server/routes/experiments/get_experiment_scores.ts:49-72`, filter builder at `x-pack/platform/packages/shared/kbn-evals-common/impl/query_builders.ts:91-104`). Exactly-one-record-per-run is already structural, not a convention this slice must impose: `computeScoreDocumentId` derives a deterministic ES `_id` from `experiment_id - suite_id - task.model.id - example.dataset.id - example.id - evaluator.name - repetition_index` (`evaluation_score_service.ts:29-40`), the write uses the `create` op so a second write with the same identity tuple returns HTTP 409 and is counted as `conflicted` (`evaluation_score_service.ts:117-140`), and this is already proven by the one real-ES integration test in the repo (`x-pack/platform/plugins/shared/evals/server/integration_tests/evaluation_score_service.test.ts:128-158`, second write all-conflicted at `:156-157`).

The work therefore decomposes into three moves, all in-place. (1) Define a `WorkerEvaluationRecord` domain DTO plus a pure serializer that maps it onto the existing `IngestScoresRequestBodyInput` shape — a pre-storage mapping only, never a separately stored document, so the "no parallel record" invariant holds. (2) Add one deterministic integration test on the proven real-ES harness that writes through `EvaluationScoreService.write` and reads back through `EvaluationScoreService.search` driven by the same `buildExperimentFilterQuery` the production route runs, asserting per-field fidelity and the all-conflicted rewrite. (3) Where a required field has no first-class queryable home, stop at a tested contract seam per the operator's point-4 rule: a blocked test naming the exact API and missing field, plus implementation-adjacent documentation of the gap — no private coupling, no separate storage.

This slice is the storage-round-trip seam inside parent plan phase PD-3 (the `@kbn/evals` harness phase, shape FR-8 / FR-10 / A-3). It is deliberately narrower than PD-3's full scope: no L4 scoring, no dataset expansion, no live UI-journey/trace gate (FR-9), no deliberately-broken golden variant (A-3), no connector retry/backoff (A-4) — those are post-seam PD-3 work and are listed as Forward below. The bet resolves on a green real write/read proof plus the no-parallel-storage invariant; nothing else is in scope.

## Components

- **`WorkerEvaluationRecord` (domain DTO + serializer, new file in `@kbn/evals-common`):** the smallest type covering the required fields (capability/run identity, worker/profile/dataset version, actual outcome, evidence references, Proposal linkage, expected outcome / human-decision label, provenance) and a pure `serializeWorkerEvaluationRecord(record): IngestScoresRequestBodyInput` mapping onto the existing ingest shape. Lives in `x-pack/platform/packages/shared/kbn-evals-common` because that package already owns every type the serializer targets (`IngestScoresRequestBody`, `EvaluationScoreDocument`, `IngestScoresRequestBodyInput`, the Zod schemas, the URL and index constants) and is the shared boundary both the harness and the plugin import — so adding a type plus a pure function is a new file in an existing module, not a new package/plugin/service/registry (proposal "no new …" invariant). The serializer has zero storage coupling; it only produces the existing ingest input.
- **`worker_evaluation_record.test.ts` (deterministic integration test, new file under `evals/server/integration_tests/`):** reuses the only real-ES harness in the repo (`createTestServers` + `startES` + `createRootWithCorePlugins` + real data-stream client, as in `evaluation_score_service.test.ts:88-105`). Writes via `EvaluationScoreService.write(serializeWorkerEvaluationRecord(fixture))`, reads via `EvaluationScoreService.search({ query: buildExperimentFilterQuery(...) })` (the exact query the production route handler runs), then asserts per-field fidelity and the all-conflicted rewrite for exactly-one-record-per-run.
- **Contract-seam test + gap note (conditional):** if a required field cannot be represented by a supported existing API, a blocked/failing sibling test naming the exact API and missing field, plus a short note in an implementation-adjacent doc in the same package. Produced only if the seam is hit (see Data Model / Failure Modes).

## Data Model

The `WorkerEvaluationRecord` is a pre-storage domain shape; the stored artifact is always the existing `EvaluationScoreDocument`, one per run. The serializer's job is to route each required field into the storage home the existing schema already supports. The ingest schema (`x-pack/platform/packages/shared/kbn-evals-common/impl/schemas/scores/ingest_scores_route.gen.ts`) is OpenAPI-generated and defines the representable surface; the table below is the field-mapping that drives the serializer and the test's fidelity assertions.

| `WorkerEvaluationRecord` field | Storage home | First-class & queryable? | Schema anchor |
|---|---|---|---|
| run identity (`runId`) | `experiment_id` + `metadata.execution_id` | yes (keyword); readable via `experiment_id` or `metadata.execution_id` | `ingest_scores_route.gen.ts` top-level + `metadata`; route `get_experiment_scores.ts:58-62` |
| capability identity (`capabilityId`) | `metadata.suite_id` | yes (`metadata.suite_id`); enters the deterministic `_id` via `DEFAULT_SUITE_ID` fallback | `evaluation_score_service.ts:26,30`; `query_builders.ts:98` |
| dataset identity (`dataset.name`) | `example.dataset.id` + `example.dataset.name` | yes (id/name) | `ingest_scores_route.gen.ts` `example.dataset` |
| dataset **version** | `evaluator.metadata.dataset_version` (flattened) | queryable only via `evaluator.metadata`; no first-class field | `evaluator.metadata` catchall |
| worker **version** | `evaluator.metadata.worker_version` (flattened) | queryable only via `evaluator.metadata` | `evaluator.metadata` catchall |
| profile **version** | `evaluator.metadata.profile_version` (flattened) | queryable only via `evaluator.metadata` | `evaluator.metadata` catchall |
| actual outcome | split: `evaluator.label` (≤256) + `evaluator.score` (float) are the queryable channels; full detail verbatim in `task.output` (stored, **not** queryable, `object enabled:false`) | partial | `evaluator.label/score`; `task.output` catchall |
| evidence references | single primary trace → first-class `evaluator.trace_id`; structured/multiple refs → `evaluator.metadata.evidence_refs` (flattened) | partial | `evaluator.trace_id` + `evaluator.metadata` catchall |
| Proposal linkage | `evaluator.metadata.proposal_id` (flattened) | queryable only via `evaluator.metadata`; no first-class field | `evaluator.metadata` catchall |
| expected outcome / human-decision label | expected ground truth via the dataset's `example.output`; human decision → `evaluator.metadata.decision` (flattened); also expressible as `evaluator.label`/`explanation` | partial | `evaluator.label/explanation`; `evaluator.metadata` catchall |
| provenance (git/ci/hostname/model) | top-level `metadata.git` / `metadata.ci` / `metadata.hostname` + `task_model` + `evaluator_model` | yes | `ingest_scores_route.gen.ts` strict `metadata` object |

The load-bearing constraint is the shape of the top-level `metadata` object: it is a **strict** `z.object` with exactly six named fields (`execution_id`, `suite_id`, `total_repetitions`, `hostname`, `git`, `ci`) and rejects arbitrary keys, whereas `scores[].evaluator.metadata` is `z.object({}).catchall(z.unknown()).optional()` — the only arbitrary-key slot in the ingest shape, and (per research finding 4, whose ES mapping characterization is authoritative here) the only such slot that is also queryable, via the `flattened` mapping (index template at `x-pack/platform/plugins/shared/evals/server/storage/scores_index_template.ts`). Consequently worker version, profile version, dataset version, structured evidence refs, and Proposal linkage have **no dedicated first-class queryable home** and must serialize into `evaluator.metadata`. They can all be *persisted* and *queried by dotted key* — so this is a representability split, not a hard blocker, and it does not by itself trigger the operator's point-4 stop condition. The stop condition fires only if a required field needs a first-class home that neither the strict `metadata` nor the flattened `evaluator.metadata` can provide.

Serializer shape (sketch):

```ts
export interface WorkerEvaluationRecord {
  // stable capability/run identity — feed computeScoreDocumentId deterministically
  capabilityId: string;          // → metadata.suite_id
  runId: string;                 // → experiment_id (+ metadata.execution_id)
  experimentName?: string;       // → experiment_name
  evaluatorName: string;         // → evaluator.name
  exampleId: string;             // → example.id
  repetitionIndex: number;       // → task.repetition_index
  // versions (seam: no first-class queryable home)
  workerVersion: string;         // → evaluator.metadata.worker_version
  profileVersion: string;        // → evaluator.metadata.profile_version
  dataset: { name: string; version?: string }; // name first-class; version → evaluator.metadata
  // outcome (split queryable vs verbatim)
  actualOutcome: { label: string; score: number; detail: unknown };
  expectedOutcomeOrLabel?: { expected?: unknown; humanDecision?: string };
  // evidence + proposal (seam)
  evidenceRefs?: { primaryTraceId?: string; refs?: Record<string, string> };
  proposalLinkage?: { proposalId: string };
  // provenance (first-class)
  model: { task: Model; evaluator: Model };
  provenance: { hostname: string; git?: { branch?: string; commitSha?: string }; ci?: BuildkiteMetadata };
}

export const serializeWorkerEvaluationRecord = (
  record: WorkerEvaluationRecord
): IngestScoresRequestBodyInput => { /* maps each field per the table above; pins identity inputs */ };
```

Exactly-one-record-per-run is delivered by feeding the serializer stable identity inputs so `computeScoreDocumentId` produces a deterministic `_id`; the existing `create`-op + 409-conflict path (`evaluation_score_service.ts:117-140`) then makes re-writes idempotent. The test asserts this directly.

## Failure Modes

- **A required field has no representable home (stop condition, operator point 4):** if a field cannot be stored even inside `evaluator.metadata`, the serializer is not patched around. A blocked/failing integration test is added that names the exact API (`IngestScoresRequestBody` / `EvaluationScoreDocument`) and the missing field, the gap is recorded in implementation-adjacent documentation in the same package, and no private coupling or separate storage is introduced. Per the mapping above this is not expected to fire for *persistence*, but it is the prescribed reaction if it does.
- **A field needs a first-class (top-level, queryable) home the strict schema forbids:** the top-level `metadata` is a strict object and the schema is generated ("Do not edit manually", `ingest_scores_route.gen.ts`). A worker field that must be top-level cannot be added in-slice; it is routed to `evaluator.metadata`, and if first-class queryability is a hard requirement, that becomes the contract-seam stop (blocked test + gap note) rather than a schema edit.
- **Lossy actual-outcome channel:** `evaluator.label` is capped at 256 chars, so a long actual outcome cannot be queried verbatim — it survives only in the unqueryable `task.output`. The serializer preserves full detail in `task.output` and a queryable digest in `label`/`score`; the split is documented, not hidden.
- **Non-deterministic identity → duplicate records (exactly-one violated):** if any identity input (`experiment_id`, `suite_id`, model id, dataset id, example id, evaluator name, repetition index) is allowed to vary per run, `computeScoreDocumentId` yields a new `_id` and re-writes create duplicates. The serializer pins these from the record's stable identity fields, and the test's all-conflicted-rewrite assertion (`evaluation_score_service.test.ts:156-157` precedent) guards the invariant.
- **Feature-flag cargo-cult:** the proposal requires the feature flag stay default off, but a pure serializer + deterministic storage test has no runtime consumer to gate — the flag belongs to the worker runtime (PD-2 / shape FR-12 / NFR-2), not this slice. Forcing an `experimentalFeatures` flag here would be noise. The slice honors the requirement by not exporting or wiring the serializer into any default-on runtime path, and by recording where the real flag lives. (Forward: tasks — confirm with the operator whether an inert flag token is still wanted.)
- **Out-of-slice flakiness (A-4) explicitly deferred:** this test has no live model connector, so rate-limit/timeout non-determinism does not apply here; connector retry/backoff is post-seam PD-3 work.

## Alternatives Considered

- **Host the serializer in a new `kbn-evals-suite-fpr` package:** rejected — a new package is explicitly forbidden by the proposal's "no new package" invariant, and (confirmed) no `fpr`/`daybreak` code module exists in this checkout today; the names appear only under `openspec/changes/`.
- **Store `WorkerEvaluationRecord` as its own ES index or Saved Object:** rejected — violates "no Elasticsearch index, no Saved Object, no parallel record," and would discard the already-proven `computeScoreDocumentId` idempotency and the mature `.evaluation-scores` data stream.
- **Host the DTO inside the `evals` platform plugin (server runtime):** rejected — it would push worker-domain knowledge into the platform plugin that owns `EvaluationScoreService` and the routes, coupling the platform to a specific worker's record shape. A pure type in the shared `@kbn/evals-common` boundary keeps the dependency one-way (serializer → existing ingest types).
- **Add new first-class fields to the strict `metadata` schema to give versions/Proposal linkage a top-level home:** rejected for this slice — the schema is OpenAPI-generated and shared across all eval consumers; widening it is a platform-schema change beyond a storage-round-trip seam and would itself be the contract-seam stop condition rather than a quiet edit.
- **Prove the round-trip through the full HTTP `EvalsClient` (live Kibana server) rather than the storage layer:** rejected as the primary proof — no deterministic precedent exists for it (the route tests at `server/routes/scores/ingest_scores.test.ts` and `server/routes/experiments/get_experiment_scores.test.ts` exercise the routes against a **mocked** `evaluationScoreService`, and `EvalsClient` is never run against real ES in any test). The storage-layer harness at `integration_tests/evaluation_score_service.test.ts` is the only deterministic real-ES path and already runs the exact `write` + `search` + `buildExperimentFilterQuery` code the HTTP route delegates to. A full HTTP round-trip is a heavier, no-precedent lift and is left as a Forward risk, not the seam's proof.

Forward: specs — the field-mapping table above is the contract the spec story should encode (write/read round-trip, field-fidelity per row, exactly-one-record-per-run, no-parallel-storage invariant, and the contract-seam stop condition).
