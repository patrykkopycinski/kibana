Overview

The Task Scheduler is a Kibana-style plugin that manages deferred and recurring work across the Acme Platform. It lets other plugins register task types, schedule instances of those types, and rely on the scheduler to execute them with retry semantics, distributed locking, and observability. It powers background jobs like report generation, alert evaluation, and data roll-ups.

Key takeaway: The scheduler uses an Elasticsearch index as its backing store and a polling loop for claim-based execution. Understanding the claim cycle is the single most important concept for working with this plugin.

Architecture

The plugin is split into a server side (scheduling, polling, execution) and a public side (management UI for viewing and cancelling tasks). The server side is the core.

Plugin registers task type
↓
Task instance scheduled
Written to .task_manager index
↓
Poll cycle runs (every 3s)
↓
Claim task via update-by-query
Distributed lock — only one node claims each task
↓
Execute task handler
↓
Success → reschedule or mark complete Failure → increment attempts, back off

Component boundaries

  • TaskStore — Elasticsearch CRUD for the .task_manager index
  • TaskPool — manages concurrency (max workers per node)
  • TaskPoller — interval-based loop that triggers claim cycles
  • TaskRunner — executes a single task instance and handles result/error
  • TaskScheduling — public API for other plugins to schedule/cancel tasks

How It Works

1. Task type registration

During setup(), consuming plugins call taskScheduler.registerTaskDefinitions() with a task type ID, a handler function, and options (timeout, max attempts, schedule).

taskScheduler.registerTaskDefinitions({
  'alerting:evaluate': {
    title: 'Evaluate alert rule',
    createTaskRunner: (context) => ({
      async run() {
        const result = await evaluateRule(context.taskInstance.params);
        return { state: result, schedule: { interval: '1m' } };
      },
    }),
    timeout: '30s',
    maxAttempts: 3,
  },
});

2. Scheduling

A task instance is created by calling taskScheduler.schedule(). This writes a document to the .task_manager index with status idle, the params, and the next run-at timestamp.

3. Polling and claiming

Every 3 seconds (configurable), each node runs a claim cycle. It issues an update_by_query against the index, atomically claiming up to maxWorkers - runningTasks idle tasks whose runAt is in the past. The claim sets status: running and ownerId to the current node.

4. Execution

TaskRunner invokes the handler registered for the task type. If the handler returns a schedule, the task is rescheduled. If it throws, the task is marked as failed, attempts are incremented, and a backoff delay is applied before the next retry.

5. Retry and failure

Tasks that exceed maxAttempts are marked failed permanently. The backoff strategy is exponential with jitter: delay = min(baseDelay * 2^attempts + random(0, jitter), maxDelay).

Configuration & Setup

Plugin configuration (acme.yml)

xpack.task_scheduler:
  enabled: true
  poll_interval: 3000        # ms between claim cycles
  max_workers: 10             # concurrent tasks per node
  max_attempts: 3             # default retry limit
  request_timeout: 30000      # ms per task execution

Feature flags

No feature flags — the plugin is always enabled when installed. Individual task types are registered by their owning plugins.

Local development

Start the platform with yarn start. The .task_manager index is created automatically on first task schedule. Use the management UI at /app/task_scheduler to inspect running and failed tasks.
