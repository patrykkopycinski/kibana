# Research: PD-2 Worker Core — ai.agent Wiring and Evidence/Proposals Source Recovery

## Research Question
Can PD-2's Reason phase invoke the existing `alert-analysis` Agent Builder skill through a real, already-registered workflow step type, and does the `server/client/evidence/`/`server/client/proposals/` `.ts` source referenced by the S0 intent actually exist anywhere recoverable in the `daybreak-spike` worktree?

## Summary
The `ai.agent` workflow step type (`RunAgentStepTypeId = 'ai.agent'`) is real, registered, and shipped — it is not illustrative. The `alert-analysis` Agent Builder *skill* is real, already registered, and untouched by this plan; however, no Agent Builder *agent* named `alert.triage` (or any agent scoped to `skill_ids: ['alert-analysis']`) exists anywhere in the repo — the only built-in agent found is the generic `elastic-ai-agent`, which by default exposes all skills (`skill_ids: []` in its create request means "all skills," per the type comment). Separately, the proposal's claim that `server/client/evidence/` and `server/client/proposals/` `.ts` source is "already written, uncommitted" does not hold: only compiled `target/types/**/*.d.ts` declaration files exist on disk in the `daybreak-spike` worktree, there are zero commits touching `server/client/*` in `git log --all`, and `git stash list` is empty. The `.d.ts` shapes are usable as a faithful reference for re-authoring, but the source itself must be written from scratch.

## Detailed Findings

### 1. `ai.agent` is a real, registered workflow step type — not a raw connector sub-action
The `ai.agent` step type is defined in `x-pack/platform/plugins/shared/agent_builder/common/step_types/run_agent_step.ts:21` (`export const RunAgentStepTypeId = 'ai.agent'`) with a Zod input schema (`message`, optional `schema` for structured output, optional `attachments`, optional `conversation_id`) and a Zod config schema (`agent-id`, `connector-id`/`inference-id` — mutually exclusive, `create-conversation`, `plugin-id`, `aggregate-by`). It is registered with the Workflows Extensions plugin at plugin-setup time in `x-pack/platform/plugins/shared/agent_builder/server/plugin.ts:128-131` via `setupDeps.workflowsExtensions.registerStepDefinition(getRunAgentStepDefinition(this.serviceManager))`. The server-side handler lives at `x-pack/platform/plugins/shared/agent_builder/server/step_types/run_agent_step.ts:28-159` and calls `serviceManager.internalStart.execution.executeAgent(...)`, consuming a `round_complete` event off an observable stream. This confirms PD-1's README claim (`server/workflow/README.md`, "What PD-2 must account for," item 1) that a purpose-built step exists to swap in for the stub `inference` connector step.

### 2. Raw `inference.*`/connector-family AI steps are formally deprecated in favor of `ai.*`
`src/platform/packages/shared/kbn-workflows/spec/deprecated_step_metadata.ts:53-57` lists a `DEPRECATED_STEP_PREFIX_METADATA` table that marks any step type starting with `inference.`, `bedrock.`, `gen-ai.`, or `gemini.` as deprecated, with `replacementStepType: 'ai.prompt'` (a sibling to `ai.agent` for non-agent prompt calls). The PD-1 spike's `analyze_alert` step (`server/workflow/spike_workflow.yaml:39-43`) used `type: inference` with `connector-id: inference_connector` — this was a deliberate stub only (per PD-1's README, "What PD-2 must account for," item 1), and PD-2 replacing it with `ai.agent` is consistent with the deprecation table, not merely a style preference.

### 3. `invoke_agent.yml`'s `agent-id: alert.triage` is illustrative, not a real registered agent
The example workflow at `src/platform/packages/shared/kbn-workflows/spec/examples/invoke_agent.yml:16-21` uses `agent-id: alert.triage`. A repo-wide search for `'alert.triage'` as a literal agent id (`grep -rn "id: 'alert.triage'"` across `x-pack/` and `src/`) returns zero matches. The only concrete agent-registration code found is the default agent's create request at `x-pack/platform/plugins/shared/agent_builder/server/routes/agents.ts:12-27` (`getDefaultAgentCreateRequest`, id `agentBuilderDefaultAgentId = 'elastic-ai-agent'`, defined at `x-pack/platform/packages/shared/agent-builder/agent-builder-common/agents/definition.ts:23`), and the agent registry's builtin-provider enumeration at `x-pack/platform/plugins/shared/agent_builder/server/services/agents/agent_registry.ts:141-144`. No second builtin agent definition file (e.g. for alert triage) exists in the registry. This directly answers the proposal's first Open Question: the workflow-invocable *agent* wrapping `alert-analysis` does **not** already exist; PD-2's opening task must create one (or bind `ai.agent`'s `agent-id` to the existing default agent, see Finding 4).

### 4. Agents and skills are distinct concepts — `skill_ids` is the binding mechanism
`AgentConfiguration` (`x-pack/platform/packages/shared/agent-builder/agent-builder-common/agents/definition.ts:82-131`) has an explicit `skill_ids?: string[]` field with the doc comment "Optional list of skill IDs exposed to the agent. When undefined, all skills are available (backward compatibility)." The default agent's create request (`x-pack/platform/plugins/shared/agent_builder/server/routes/agents.ts:22-27`) sets `skill_ids: []` and `enable_elastic_capabilities: true`. This means a minimal Agent Builder agent scoped to only the `alert-analysis` skill can be created by supplying `configuration.skill_ids: ['alert-analysis']` on an `AgentCreateRequest` via the agents service's `create` method (invoked at `x-pack/platform/plugins/shared/agent_builder/server/routes/agents.ts:312`, `service.create(request.body)`) — this is the concrete mechanism for PD-2's A-1-resolution opening task, whether that task creates a new agent or (if acceptable) reuses `elastic-ai-agent` with its default all-skills access.

### 5. The `alert-analysis` skill is real, registered, and tool-scoped as the proposal describes
`x-pack/solutions/security/plugins/security_solution/server/agent_builder/skills/alert_analysis/alert_analysis_skill.ts:23-148` defines `alertAnalysisSkill` with `id: 'alert-analysis'`, registry tools `SECURITY_ALERTS_TOOL_ID`, `SECURITY_LABS_SEARCH_TOOL_ID`, `SECURITY_ENTITY_RISK_SCORE_TOOL_ID` (lines 93-97), and one inline tool `security.alert-analysis.get-related-alerts` (lines 98-146) backed by `findRelatedAlerts`. It is registered unconditionally (no feature flag) in `register_skills.ts:81` (`await agentBuilder.skills.register(alertAnalysisSkill);`), imported via `x-pack/solutions/security/plugins/security_solution/server/agent_builder/skills/index.ts:8` from the `./alert_analysis` subdirectory. A same-named but structurally different file, `.../skills/alert_analysis_skill.ts` (no subdirectory), also exists on disk but is **not** imported by `index.ts` or `register_skills.ts` — it is dead/superseded code, confirmed by `git log` showing the subdirectory version landed via PR #269397 ("Alert analysis inline-api-tool skill (v3)"). PD-2 must be careful to reference the registered `./alert_analysis` skill, not the unused sibling file, when citing "the alert-analysis skill" in design/tasks.

### 6. The S0 `server/client/evidence/` and `server/client/proposals/` `.ts` source does not exist — only compiled `.d.ts` output does
A file listing of `x-pack/solutions/security/plugins/daybreak/` on the `daybreak-spike` worktree (via SSH to the `kibana-i9` host, since this plugin was scaffolded only on the attached worktree, not the local checkout) shows a `target/types/server/client/evidence/{client,index,storage,types}.d.ts` and `target/types/server/client/proposals/{client,gate,gate.test,index,storage,types}.d.ts` — six-plus declaration files — but **no corresponding `.ts` files** anywhere under `server/client/`. `git log --all --oneline -- 'x-pack/solutions/security/plugins/daybreak/server/client/*'` on that worktree returns zero commits, and `git stash list` is empty. This confirms the proposal's own finding: the S0 intent's claim that this code "already exists, uncommitted" is false for the source; only the compiled build artifact survives, and it must be treated purely as a type-shape reference (per the proposal's "What Changes" and "Hard Constraints" sections), not as a scaffold.

### 7. The `.d.ts` files fully specify the Evidence and Proposal domain shapes needed for re-authoring
`evidence/storage.d.ts:42-53` gives the full `EvidenceProperties` interface (`id, kind, sourceRef?, summary, provenance, confidence, stance, limitations?, sensitivityLabel, createdAt`) plus the ES index name `.daybreak-evidence` (line 4) and a `StorageIndexAdapter`-typed storage settings shape with snake_case ES field names (`source_ref`, `sensitivity_label`, `created_at`). `evidence/client.d.ts:6-39` gives the full `EvidenceClient` interface (`get/list/create/update/delete`) and parameter types. `proposals/types.d.ts:1-56` gives `ProposalStatus` (7 values including `'approved'`), `ProposalProperties` (`id, title, sourceWatch?, capability, severity, confidence, status, owner?, createdAt, recommendation?, evidenceRefs, expectedImpact?, riskCaveats?, approvalRequirement?, decisionHistory, space?`), and `DecisionHistoryEntry`. `proposals/gate.d.ts:16-40` gives the exact fail-closed contract: `evaluateReadinessGate`/`requireReadinessGate` check, for `targetStatus === 'approved'` only, that `evidenceRefs` is non-empty AND `recommendation` is non-empty, returning a `GateResult` discriminated union (`{approved:true,...} | {approved:false, failure: GateFailure}`) where `GateFailure.missingRequirements` is typed as `('evidence' | 'recommendation')[]`. `proposals/storage.d.ts` and `proposals/client.d.ts` additionally show the ES-side document uses `evidence_refs: {ref_id: string}[]` (an object array, not a bare string array) even though the client-facing `ProposalProperties.evidenceRefs` is `string[]` — this snake_case/object-wrapping translation is a re-authoring detail downstream tasks must reproduce faithfully, not simplify away.

### 8. `WorkflowRunFixture` and `FakeConnectors` are the established integration-test harness for PD-2's new test
The fixture used by PD-1's `workflow_engine_shape.test.ts` lives at `src/platform/plugins/shared/workflows_execution_engine/integration_tests/workflow_run_fixture.ts`, imported as `@kbn/workflows-execution-engine/integration_tests/workflow_run_fixture` in the daybreak test file. `FakeConnectors` (`.../integration_tests/mocks/actions_plugin_mock/index.ts:12-55`) enumerates stub connectors including `echo_inference`, `slow_3sec_inference`, `slow_3sec_failing_inference`, and `large_response` — the `slow_*_failing_inference` and `slow_*_inference` stubs are directly usable for A-4's retry/backoff and timeout-handling test cases in a future PD-3 eval harness, and for PD-2's own fail-closed integration test (Finding 9). The existing `workflow_engine_shape.test.ts:79-157` pattern (`getStepExecutions` helper reading `fixture.stepExecutionRepositoryMock.stepExecutions`) is the concrete pattern PD-2's Definition of Done references as "extending PD-1's `WorkflowRunFixture` pattern."

### 9. PD-1's README already documents that fail-closed-on-error is a boundary concern, not an engine feature
`server/workflow/README.md` ("Engine limitations discovered," item 3) states plainly: "Fail-closed on error is NOT an engine built-in... fail-closed behavior *on a step error or inference timeout* is not provided by the engine; it is a boundary concern that the worker (PD-2) must enforce itself." This is direct prior-art grounding for the proposal's "Add the output-validation guard (hook 5, FR-6) as an explicit workflow step... between Reason and Act" — it must be authored as an explicit step (or engine-level `on-failure`/guard construct), not assumed to be automatic.

### 10. The `ai.agent` step's `connector-id`/`inference-id` are both optional, with silent fallback
`resolveConnectorOrInferenceId` (`x-pack/platform/plugins/shared/agent_builder/common/resolve_connector_or_inference_id.ts:37-45`) returns `connector ?? inference`, i.e. `undefined` when both are omitted, and throws a `ConnectorOrInferenceIdConflictError` only when both are set. The `ai.agent` step handler (`run_agent_step.ts:60-64`) computes `effectiveConnectorId` this way and passes it into `executionService.executeAgent(...)`'s `params.connectorId`. This means the workflow YAML does not have to specify a connector at all — the execution service applies its own default-connector resolution downstream. This partially answers the proposal's second Open Question (which `.inference`/`.eis-*` connector-id to use): omitting `connector-id`/`inference-id` entirely is a valid, code-supported option if the dev stack's default GenAI connector is acceptable for the spike; **Forward: design** — confirming what that default resolves to on the i9 dev stack (and whether the demo needs it pinned) still requires a live-stack check, not a code-only answer.

## Open Questions
- Forward: design — the dev stack's default GenAI connector resolution when `connector-id`/`inference-id` are both omitted on `ai.agent` (Finding 10) was confirmed as code-supported but not verified against a live i9 dev-stack connector list; design should either confirm the default is acceptable for the demo or pin an explicit connector-id.
- Forward: design — whether to (a) create a new minimal agent scoped to `skill_ids: ['alert-analysis']` via `service.create(...)` (Finding 4), or (b) invoke `elastic-ai-agent` directly (which already has access to all skills including `alert-analysis` by default) — the proposal's Impact section frames this as "PD-2's opening task," but the code shows option (b) requires zero new agent-creation code; the choice affects whether PD-2's Definition of Done needs an additional committed agent-scaffolding artifact.
- The dead/unused sibling file `x-pack/solutions/security/plugins/security_solution/server/agent_builder/skills/alert_analysis_skill.ts` (Finding 5) was not further investigated for why it still exists on disk unreferenced — out of scope for this research pass since the proposal's "What Changes" does not touch skill registration, but noted so downstream tasks don't accidentally edit the wrong file.
