# Research: PD-4 Kibana UI Panel aligned to the Throughline (NotDaybreak) prototype

## Research Question
Does the repository actually contain the things the proposal builds on — the vendored Throughline prototype, the daybreak plugin's server-side Evidence/Proposal stores, the plugin's `public/` layer, its experimental flag, its HTTP API, and the PD-3 eval primitives — in the form and location the proposal assumes?

## Summary
It does not, in nearly every case. The Throughline prototype (`docs-site/prototype/`) is absent from the working tree and from all git history, so every symbol/line citation the proposal relies on is unverifiable. The daybreak plugin exists only on remote `daybreak-spike` branches (PD-1/PD-2 work) — it is **not** present in the named feature worktree's HEAD — and even there it is server-only with no `public/` directory, no `experimentalFeatures` flag, and no HTTP API exposing the stores. The one premise that holds: PD-4 building a new `public/` layer is genuinely greenfield. The real, citable artifacts are the PD-2 `Proposal` and `Evidence` store type/contract shapes (which do exist on the spike branch) — these are what a UI must actually render and are documented below.

## Detailed Findings

### 1. The Throughline prototype — the proposal's design source-of-truth — is absent from the repository and from all git history
The proposal states the UI's "visual + interaction source-of-truth is the vendored Throughline prototype at `docs-site/prototype/`" and instructs porting from `throughline-app.js` / `Throughline.dc.html` / `support.js`. None of these exist:
- There is no `docs-site/` directory. The repository's top-level directories are `config/`, `dev_docs/`, `docs/`, `examples/`, `legacy_rfcs/`, `licenses/`, `oas_docs/`, `openspec/`, `packages/`, `plugins/`, `scripts/`, `src/`, `typings/`, `x-pack/`. The `docs/` directory is Elastic's documentation (asciidoc changelogs/reference), containing no HTML application prototype.
- No `*.dc.html`, `throughline-app.js`, or `support.js` exists anywhere in the working tree.
- `git log --all -- "*throughline*"` and `git log --all -- "docs-site/prototype/*"` both return empty — the prototype has never been committed on any branch.

Consequently **every** prototype symbol and line reference in the proposal is unverifiable: `TL_CSS` (~3), `TL_SHELL` (~4), `renderApp` (~5983), `renderRail` (~4897), `renderNav` (~1466) + `navMenuItem` + `STATUS_RANK`, `renderStage` (~4960), `renderStream` (~3798), `renderMsg` (~3819), `renderSpine` (~3759), `renderObjectApp` (~3948), `renderInspector` (~5937), `renderInspBody` (~3974), `TYPE_META` (~1153), `briefView` (~2868), `BRIEF_EXTRA_CSS` (~6), `syncChatDock` (~1519), `renderSuggest` (~4055), plus `STATUS_DOT`, `SEV`, `gate-yes`/`gate-ic`. Not one can be grounded in a `file:line`. These are recorded as Open Questions rather than findings, per the evidence contract.

### 2. The named feature worktree contains no daybreak code at all; the plugin lives only on remote `daybreak-spike` branches
The operator description says to "reuse" worktree `ao/feat-daybreak-s1-alert-analysis-worker-spike` and build "on the `public/` side of an existing plugin." But the current branch HEAD (`ec14270513eb`) is a mainline commit and contains zero daybreak files. The daybreak commits (PD-1 scaffold + PD-2 worker core) are **not** ancestors of HEAD. They exist only on `origin/daybreak-spike` (tip `2cbad6ad0e78` as of 2026-07-09; corrected up from `33a054f1afad` after 3 commits that existed only on the worker mirrors `i9/daybreak-spike` and `m1max/daybreak-spike-sync` — the Reason/`ai.agent` integration test, the readiness-gate Act test, and the `run_alert_analysis_worker.ts` runner — were reconciled/pushed to `origin/daybreak-spike`), `i9/daybreak-spike`, and `m1max/daybreak-spike-sync`. `origin/daybreak-spike` diverged from mainline at `0eaa6d0b2207`. The only `daybreak`-named content in the working tree is the `openspec/` change directory (this artifact). So before any UI work, the PD-1/PD-2 output must be brought onto the feature branch (merge or checkout `daybreak-spike`).

**Confirmed remaining gap (not resolved by pushing the above commits):** PD-2 task 1.3 specified `x-pack/solutions/security/plugins/daybreak/server/workflow/enrich_alert_schema.test.ts` asserting an `alertInputSchema` (Zod) rejects malformed input and a `packageEvidence` function producing a framing/rubric-free ground-truth block (FR-009, FR-018, FR-019, NFR-4). No file of that name and no `alertInputSchema`/`packageEvidence` symbols exist on `origin/daybreak-spike`, `i9/daybreak-spike`, or `m1max/daybreak-spike-sync` as of `2cbad6ad0e78`. The Enrich phase in the shipped `alert_analysis_worker.yaml` is a bare `kibana.request` step (`GET /internal/detection_engine/signals/_alerts_summary`) with no input-validation module — this is a genuine, unresolved PD-2 deliverable gap, not a task-status desync artifact.

### 3. The daybreak plugin is server-only; no `public/` directory exists even on the spike branch
The plugin manifest (`kibana.jsonc`) declares `"browser": false, "server": true`. A full recursive listing of `x-pack/solutions/security/plugins/daybreak/` on `origin/daybreak-spike` shows `common/`, `server/`, `kibana.jsonc`, `tsconfig.json`, and jest configs — and **no `public/` directory**. So PD-4's "build the `public/` layer" is genuinely greenfield (that part of the premise is correct), but the "existing plugin" has no browser side to extend.

### 4. There is no "daybreak" `experimentalFeatures` flag and no application route today
The proposal's acceptance gate says to "register a Kibana application route under the existing `daybreak` experimental flag (default off)" and NFR-2 specifies a feature flag "via `experimentalFeatures`." Neither matches the code. The only gate is a config schema: `xpack.daybreak.enabled`, `schema.boolean({ defaultValue: false })` in `common/config.ts`. There is no `experimentalFeatures` entry for daybreak anywhere. Because the plugin is server-only, it registers no application route at all today. (The `config.ts` comment calls `enabled` "an experimental feature flag," but the mechanism is a server config setting, not an `experimentalFeatures` capability.) Forward: design/specs must decide whether adding `browser: true`, an `experimentalFeatures` registration, and an application route is in PD-4's scope — the current code has none of these.

### 5. The PD-2 Evidence and Proposal stores exist on the spike branch — these are the real data contracts a UI must render
The path the proposal cites, `x-pack/solutions/security/plugins/daybreak/server/client/`, is accurate on the spike branch, split into `evidence/` and `proposals/`. These are the only real, citable contracts relevant to PD-4. The shapes (relevant to FR-4 "Enrich/evidence," FR-7 "Act/Proposal," and the gate-approval flow):

- **Proposal** (`proposals/types.ts`): `ProposalStatus` is a 7-value union — `new | needs-evidence | approved | modified | dismissed | escalated | deferred`. `ProposalProperties` has: `id`, `title`, `sourceWatch?`, `capability`, `severity` (`low|medium|high|critical`), `confidence` (number), `status` (ProposalStatus), `owner?`, `createdAt`, `recommendation?`, `evidenceRefs` (string[]), `expectedImpact?`, `riskCaveats?` (string[]), `approvalRequirement?` (`manual|automatic`), `decisionHistory` (DecisionHistoryEntry[]), `space?`. `DecisionHistoryEntry` = `fromStatus`, `toStatus`, `actor?`, `reason?`, `timestamp`.
- **Approval/readiness gate** (`proposals/gate.ts`, FR-7 hook 7): `evaluateReadinessGate(proposal, targetStatus)` returns a discriminated `GateResult` (`{approved:true}` | `{approved:false, failure}`). Transition to `approved` fails closed unless `evidenceRefs` is non-empty AND `recommendation` is non-empty; all other target statuses pass. `requireReadinessGate` throws `ReadinessGateError` on failure. `MissingRequirement` is `'evidence' | 'recommendation'`. This is the server-side gate PD-4's gate-approval UI would call.
- **Evidence** (`evidence/types.ts` + `evidence/storage.ts`): `EvidenceProperties` has `id`, `kind` (`alert|event|entity|timeline|query|assumption|external`), `sourceRef?`, `summary`, `provenance` (`capability|skillVersion|tool`), `confidence` (number), `stance` (`for|against`), `limitations?` (string[]), `sensitivityLabel` (`public|internal|restricted`), `createdAt`, `space?`. `EvidenceDocument` is an ES `GetResponse` wrapper around it.

These map conceptually to the prototype's Proposal/gate/severity/evidence concepts, but the prototype's own UI symbols (SEV, STATUS_DOT, STATUS_RANK, gate-yes/gate-ic) cannot be verified against the missing prototype.

### 6. No HTTP API exposes the stores; the proposal's "real data wiring" needs server routes that do not exist
The proposal's "Data wiring (not mocked)" item says the UI reads "real data from the plugin's HTTP API → the PD-2 Evidence store and Proposal store." A `git grep` for `createRouter` / `router.get|post|put|delete` / `http.` across the entire daybreak `server/` tree on the spike branch returns **nothing**. `server/plugin.ts` `setup()` returns `{}` and `start()` returns only `{ runSpikeWorkflow }` (wiring `workflowsExecutionEngine.executeWorkflow`). The evidence/proposals modules are programmatic ES-backed storage clients consumed by the workflow; they are not exposed over HTTP. Building the UI's data layer therefore requires first authoring server routes (a scope item not stated in PD-4's "What Changes").

### 7. Plan/dependency state: PD-2 is still active and PD-3 (eval harness) is not registered
The feature's own context file `.ao/context.json` records `activePlanId: "daybreak-s1-pd2-worker-core"` and a plans list of only `daybreak-s1-pd1-workflow-engine-spike` (`completed`) and `daybreak-s1-pd2-worker-core` (`active`). There is no registered PD-3 plan, so the `@kbn/evals` harness and "eval primitives" PD-4 is told to reuse (FR-9, per "reuse the PD-3 eval primitives; do not build a parallel harness") do not yet exist as produced code. PD-4's UI-journey eval therefore has no existing harness to reuse, and PD-2 (its server dependency) is not finished.
