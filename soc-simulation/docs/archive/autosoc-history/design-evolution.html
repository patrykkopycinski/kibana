Design Evolution: Agent vs. Deterministic

Lessons from building the Autonomous SOC Recommendations system — and why Agent-First isn't always best
Learnings April 2026
Thesis

When building AI-powered automation, the instinct is to give agents maximum autonomy. We started there. After multiple production failures, we arrived at a hybrid architecture where agents recommend and deterministic code executes. This document traces every failure and the architectural pivots they forced — so the team can learn from the iteration rather than repeat it.

1 Starting Point: Pure Agent Autonomy

The initial design gave AI agents full control over the action loop. The Detection Engineering Agent would analyze alert data, decide what rules needed tuning, and directly apply changes — exceptions, threshold adjustments, new rules — all in one pass.

Agent's job (v1)

Query outcomes → Analyze FP rates → Decide action → Execute action via tools → Log result

Human's job

Observe logs. Trust the agent. Intervene if something looks wrong (reactive).

This is the "agent-first" pattern: the LLM is the decision-maker and the executor. It felt right. It was fast to prototype. And it failed in every way imaginable.

2 Failure Timeline

Each failure below was discovered in production (the running simulation) and forced an architectural change.

Failure #1 — Ghost Exceptions

Agent claimed it applied an exception. It didn't exist.

The DetEng agent's output said "action": "add_exception" with a rule ID and exception spec. The workflow logged it as "applied." The SOC dashboard showed ✓ Applied. But when we checked the actual rule in Kibana — no exception existed.

Root cause

The agent had read-only tools (security.alerts, platform.core.search). It could describe the exception it wanted to create, but it had no tool to actually call POST /api/detection_engine/rules/{id}/exceptions. It hallucinated success in its output because the instruction said "apply the exception" — so it narrated doing so.

Impact False sense of security. Analysts believed FP rules were patched when they weren't.

Failure #2 — One-shot workflow hallucination

Meta Agent "created" a workflow that never deployed.

After giving agents the platform.workflows.workflow_set_yaml tool, the Meta Agent attempted to create a one-shot workflow containing a kibana.request step to apply the exception. The workflow YAML it generated was syntactically valid but semantically wrong — it referenced a non-existent connector, used incorrect step types, and the workflow engine silently rejected it.

The agent's output: "Successfully deployed one-shot workflow for exception application." Reality: the workflow didn't exist.

Root cause

LLMs generate plausible-looking YAML, not correct YAML. The workflow engine's validation errors were swallowed, and the agent couldn't verify its own output. There's no feedback loop between "I deployed a workflow" and "the workflow actually ran and the exception now exists."

Failure #3 — Parsing fragility

Exception entries parsed wrong → API rejected with "Bad Request"

After moving exception application to the frontend (Pivot #1 below), the code needed to parse the agent's free-text after field into structured exception entries. The agent wrote: "Exception 1: process.parent.name:"cron" AND process.command_line:"*run-parts*" — Exception 2: process.parent.name:"cron" AND process.command_line:"*cron.daily*""

The parser had a fieldsSeen set that deduplicated by field name. Since process.parent.name appeared in both exceptions, the second exception was silently dropped. Worse, the value regex bled across the AND boundary, producing a wildcard entry with an array value — which the Detection Engine API rejected as a Bad Request.

Root cause

Agent output is unstructured natural language with embedded field:value pairs. Parsing it reliably requires understanding the agent's formatting conventions, which change across runs. Every new phrasing pattern broke the parser.

Impact 3 parser rewrites. Each fix broke a different edge case.

Failure #4 — Rule creation without a Kibana UUID

Agent recommended rules but couldn't create them — and no way to preview.

The DetEng agent's instructions said "create new rules as DISABLED and return the rule_id." The agent dutifully included "rule_id": "auto-generated-t1033-v1" in its output. But this was a string the agent made up — no rule existed in Kibana with this ID.

The dashboard showed the recommendation with a proposed rule config, but the "View rule" link was hidden for pending items because there was no actual Kibana rule to link to. The user had to approve blind — reading a JSON blob instead of the native rule details UI.

Root cause

The agent lacked the tools to create rules via the Detection Engine API. It could only describe the rule it wanted. The gap between "agent recommends" and "system provisions" had no bridge.

Failure #5 — Agent proliferation

Meta Agent kept spawning new sub-agents instead of reusing existing ones.

The Meta Agent's evolution strategy was: "identify a gap → create a new agent + workflow." After a few cycles, the system had 10+ custom agents, many overlapping in capability. There was soc-hunt-deep-agent, soc-anomaly-monitor, soc-correlation-engine — all essentially querying the same data with slightly different prompts.

Root cause

An LLM's default strategy for "solve this problem" is "create a new thing." Without explicit tiers (reuse → enrich → create), the cheapest cognitive path is always "new agent." This is analogous to junior engineers creating new microservices instead of adding a method to an existing one.

Impact Resource waste, connector quota exhaustion, overlapping workflows fighting each other.

5 The Pattern: Recommend / Review / Execute

The system converged on a three-phase pattern that applies to every action type. The key insight: separate the LLM's strength (reasoning) from its weakness (precise execution).

Phase 1 — Recommend

Who: AI Agent

Agent analyzes data, identifies patterns, and outputs structured recommendations. No side-effects. Read-only tools only.

LLM Strength Pattern recognition, reasoning, natural language analysis

Phase 2 — Review

Who: Human + Deterministic Bridge

Bridge provisions resources (DISABLED rules) so user can preview in native UI. Human reviews each item, sees real rule config, approves or rejects with reason.

Human Strength Judgment, context, accountability

Phase 3 — Execute

Who: Deterministic Code

Frontend or bridge calls APIs directly. Enable rule, create exception, deploy workflow. Exact API payloads. Verified responses. Immediate UI feedback.

Code Strength Precision, reliability, verifiability

Why this works

Each phase uses the right tool for the job. LLMs are excellent at analyzing 500 alerts and saying "this pattern is a false positive because of cron maintenance." They are terrible at constructing a syntactically valid POST /api/detection_engine/rules/{id}/exceptions request with the right entry types, operators, and values. By keeping them in the "recommend" lane and letting deterministic code handle execution, every action either succeeds completely or fails with a clear error.

7 Principles for Agent-Powered Systems

1. Agents recommend; code executes

Never let an LLM perform write operations directly. The moment an agent calls POST /api/… through a tool, you've lost verifiability. The agent can hallucinate success, mis-format payloads, or silently fail. Deterministic code either succeeds or throws.

2. Never trust agent output format stability

The same agent with the same prompt will format its output differently across runs. Field ordering changes, quoting conventions change, prose wrappers appear and disappear. Any parser that relies on a specific format will break. Build parsers that handle multiple conventions, and always validate before sending to APIs.

3. Preview before commit

When an agent recommends creating a resource (rule, agent, workflow), create it in a disabled/draft state immediately so the human can inspect it in the native UI. Reviewing a JSON blob is not reviewing. Reviewing a real rule in the rule details page — with query highlighting, threat mapping, and preview results — is reviewing.

4. Constrain the blast radius of LLM decisions

Left unconstrained, LLMs default to "create new things" rather than "modify existing things." A tiered strategy (reuse → enrich → create) with explicit justification requirements at each tier prevents agent sprawl and keeps the system maintainable.

5. Rejection is training data

When a human rejects a recommendation with a reason, that reason is fed back to the agent in subsequent cycles. This creates a feedback loop that doesn't require fine-tuning — the agent sees "User rejected this because the cron pattern is benign" and adjusts its future recommendations. Rejection reasons are as valuable as approvals.

6. Bridge the provision gap with workflows, not sidecars

There's often a gap between "agent recommends X" and "X exists in the system for review." A deterministic Elastic workflow (soc_autonomous_applier) polls for pending recommendations and provisions resources via native Kibana APIs — no Python sidecars. This closes the gap while keeping all governance (kill-switch, ownership, budgets, cooldowns, loop detection) in the same engine that runs everything else in the stack.

10 The Takeaway

"Agent-first" is not the same as "agent-only."

The agent is the best part of this system — it genuinely identifies patterns in alert data that would take a human analyst hours. But the moment we asked it to also be the executor, every failure mode of LLMs (hallucination, format instability, lack of verification) became a production incident. The hybrid architecture keeps the agent doing what it's brilliant at (reasoning) and hands execution to code that's brilliant at being precise.

This isn't a limitation of the current models. It's a systems design principle: separate the decision-maker from the executor, and put a human in between.

The hardening phase adds the final layer: the system must be observable, recoverable, and cost-aware. Graduated autonomy means trust is earned, not assumed. Rollback snapshots mean mistakes are fixable. Pipeline locking means concurrent runs can't corrupt state. These aren't features — they're the difference between a demo and a system.

11 Agent Consolidation — 9 → 4 Agents

Why consolidate?

The 9-agent architecture worked but created unnecessary LLM overhead. Entity enrichment and hunt investigation shared 70% of their tools with triage. Context was lost between agent hops in the pipeline (3 separate LLM calls passed JSON strings, losing nuance each time). Watchdog and difficulty evaluator were single-purpose agents that ran one tool each — skills with deterministic workflow wrappers accomplish the same at zero LLM cost.

Mandatory Self-Validation

Every agent and workflow now validates its own output before passing it downstream. This is a system-wide invariant, not an optional best practice. Validation failures are logged to .soc-evolution-log with result: "validation_failed" so the meta-agent can track patterns and improve.

Key insight

Agent consolidation is not about having fewer agents — it's about eliminating context loss between LLM calls. When triage, enrichment, and investigation are separate agents, each call starts with a JSON summary of the previous step's output. The LLM loses the reasoning chain, misinterprets fields, and makes decisions based on incomplete context. A single unified triage agent processes the alert end-to-end, maintaining full reasoning context across all phases. This produces higher-quality classifications and costs less (1 LLM call instead of 3).

Depth Extension — From Reactive to Proactive

The initial AutoSOC was structurally sound but operationally shallow — binary TP/FP classification, per-alert triage with no correlation, reactive-only hunting, and a response system that logged but never contained. The depth extension addresses five dimensions simultaneously.

Pillar 1: Richer Classification Taxonomy (6 dispositions)

Binary TP/FP is a Level-1 analyst taxonomy. The extended system classifies alerts across four independent dimensions: disposition (TRUE_POSITIVE, BENIGN_TRUE_POSITIVE, FALSE_POSITIVE, POLICY_VIOLATION, INCONCLUSIVE, DUPLICATE), threat category (commodity malware, targeted attack, insider threat, etc.), kill chain stage (mapped from MITRE ATT&CK techniques), and business impact (data at risk, systems at risk, criticality level).

This enables downstream systems to make nuanced decisions: a BENIGN_TRUE_POSITIVE doesn't need containment but does need SML baseline updates. A POLICY_VIOLATION needs HR notification, not incident response.

Pillar 2: Attack Chain Correlation

The security.attack_discovery_search tool was registered in the codebase but completely unused. We integrated it into the triage pipeline with a pre-triage correlation step that groups alerts by entity (host, user, IP) and maps MITRE techniques to kill chain stages. When alerts form a progression (Delivery → Exploitation → Installation), the triage agent treats them as a coordinated attack chain rather than isolated events.

New skill: soc-attack-chain-analysis defines the kill chain detection algorithm, confidence boosting rules, and campaign detection logic.

Pillar 3: Proactive Threat Hunting

The system now hunts for threats that haven't triggered any alert. Three hunt types:

  • Hypothesis-driven: After observing T1059 (execution), proactively query for T1071 (C2 beaconing) and T1048 (exfiltration) on the same hosts.
  • Anomaly-driven: Periodic ES|QL queries for behavioral deviations — new login sources, first-time process relationships, unusual outbound connections.
  • Intelligence-driven: When Security Labs returns new IOCs, sweep all logs for matches.

The soc_proactive_hunter workflow runs every 2 hours, and findings go to .soc-hunt-findings.

Pillar 4: Tiered Response Automation

The response system moved from a no-op (log_and_escalate) to a four-tier model:

TierNameConfidenceActionsApproval
0Observe< 40Close, no actionNone
1Record40–59Create case, tag entitiesNone
2Contain60–79Isolate host, disable account, block IOCsHuman approval
3Eradicate≥ 80Full playbook: isolate + preserve + terminateHuman approval

Tier 2+ actions use Elastic Defend response actions API (host isolation, process kill, file retrieval) and require human approval via the recommendations workflow.

Pillar 5: Self-Improving Capability Gap Analyzer

The gap analyzer makes the system self-aware of its own limitations. Running every 4 hours, it inventories all available tools, data sources, and detection rules, then compares against what the system actually uses. Signals include: unused tools, untapped data sources, incomplete kill chain coverage, classification blind spots, response gaps, stale SML baselines, rule coverage drift, and confidence calibration drift.

Findings are written to .soc-recommendations as capability_gap type, enabling the meta-agent to autonomously address the highest-impact gaps.

Key insight

The gap analyzer is intentionally the first pillar implemented because it bootstraps the others. Once running, it discovers the unused attack_discovery_search tool, the classification blind spots, and the response no-op — effectively recommending Pillars 2–4 as capability gaps. This makes the system self-extending rather than requiring manual extension for every new capability.

Self-Governance Rails & the Autonomy Pivot

With consolidation (Section 10) and depth extension (Section 11) in place, the system reached a new failure mode: it was smart enough to propose changes faster than humans could review them. Queues of .soc-recommendations grew; stale recommendations poisoned the feedback loop; and the limiting factor became human review latency, not detection quality. Section 12 is the answer — and it arrives with a hard architectural constraint: everything must run on the Elastic Stack. No custom Python sidecars.

Two-tier Ownership Model

The registry .soc-artifact-registry tags every artifact (agent, skill, workflow, rule) with one of two owners:

  • canonical — installed by setup.sh. Human-owned. NEVER auto-mutated, regardless of kill-switch state. This is the safety floor.
  • autosoc (registry value, auto-* prefix convention) — created by AutoSOC during a mutation cycle. Safe targets for autonomous exception adds, threshold tweaks, redesigns, and deprecations. All are created DISABLED for detection rules; enable is a separate gated step.

Retro-tagging at deploy time is done by the soc_registry_retro_tag workflow (pure Elastic-native — no Python). The deterministic rule is: first dash-segment of artifact_id is soc or caldera → owner=canonical; anything else → owner=autosoc. The convention for AutoSOC-created artifacts is the auto-* prefix (e.g. auto-phishing-analyzer-agent) — never autosoc-* or any variant containing soc-, to keep the prefix check unambiguous.

Five Deterministic Gates (the Rails)

Before any agent-proposed mutation is applied, five deterministic gates run in soc_autonomous_applier. Each is an Elasticsearch query or if step — no LLM reasoning is permitted at this layer.

GateCheckRejection record
1. Kill switchLatest .soc-kill-switch document with scope: global has autonomy_enabled: false (i.e. autonomy disabled)Entire applier run aborts; a single row is written to .soc-audit-trail with event_type: autonomous_applier_abort, reason: kill_switch_active
2. OwnershipTarget's owner in .soc-artifact-registry is not canonical, AND the first dash-segment of artifact_id is neither soc nor calderaresult: blocked_canonical (intent marked rejected)
3. BudgetCount of applied mutations in .soc-evolution-log over the last 24h is under daily_budget_allresult: blocked_budget (intent stays pending — deferred)
4. CooldownSame artifact_id has no result: applied row within cooldown_secondsresult: blocked_cooldown (intent stays pending — deferred)
5. Loop detectionSame artifact_id has fewer than loop_threshold attempts (applied OR failed) within loop_window_secondsresult: blocked_loop (intent marked rejected)

Only when all five pass is the mutation_intent dispatched to soc_autonomous_applier-agent, which snapshots the target to .soc-snapshots, calls the native mutation tool, updates the registry, and closes the intent. Every transition is mirrored into .soc-evolution-log.

DetEng Split — Principal vs Signal Quality

Autonomy requires clear blast-radius ownership. The single soc_deteng-agent is split into two focused agents with non-overlapping scope:

AgentOwnsDoes NOT own
soc_deteng-agent (Principal DetEng)New rules from coverage gaps · rule redesigns · deprecating stale rules · MITRE mappingFP/TP tuning · adding exceptions · threshold tweaks

The Signal Quality agent runs first in the DetEng workflow; its redesign_required flags flow to Principal DetEng on the same cycle. This creates a explicit handoff that the deterministic applier can validate — no more "agent silently disabled a rule because it was noisy."

Regression Harness

The soc_regression_harvester workflow snapshots high-signal .soc-outcomes cases into .soc-regression-dataset (rejected recommendations are kept as negative regression cases — they capture what the system should not do again). The soc_regression_gate workflow re-runs the dataset against the current triage model after every applier cycle; any regression blocks further autonomous mutations until a human acknowledges it.

Pure-Elastic Pivot

The original design had a Python meta-bridge (polling for provisioning) and a Python caldera-bridge (driving Caldera operations). Both are gone. Every side-effect now runs in a workflow using only elasticsearch.*, kibana.request, http, and foreach/if steps:

Removed (Python)Replacement (Elastic workflow)What it does

The constraint is a feature: governance state (kill-switch, budgets, registry) lives in the same engine that runs the system. One control surface. One audit log (.soc-evolution-log). One rollback mechanism (.soc-snapshots). No glue.

Key insight

Autonomy without deterministic rails is a demo; deterministic rails without autonomy is a dashboard. Section 12's bet is that governance-as-workflows — kill switch, ownership, budget, cooldown, loop detection — is the only design that lets both coexist without either side (agents or humans) becoming the bottleneck. The pure-Elastic pivot is what makes it operable: one engine, one query language, one audit index, one set of tools. When something breaks, you don't grep Python sidecars; you run an ES|QL query against .soc-evolution-log.
