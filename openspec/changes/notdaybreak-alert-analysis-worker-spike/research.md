# Research: NotDaybreak 9.5 Alert-Analysis Worker Spike

## Research Question
Does this repository already contain the infrastructure the spike bets on — a Workflow engine that expresses the 5-phase step shape (HTTP fetch → guard → AI invocation → structured output), an Agent Builder agent/skill with structured JSON output, an @kbn/evals harness with both offline-dataset and live-trace gates, a UI panel surface, and a feature flag — and which of those pieces are greenfield rather than reused?

## Summary
Most of the substrate already ships in this repo. The `workflows_execution_engine` plugin defines the required step types and a production `streams` workflow already composes an HTTP-fetch step directly into a conditional guard (resolves the spike's highest-uncertainty item favorably). The Agent Builder `ai.agent` step passes a Zod-derived schema to the execution service and fails closed on missing/errored output, and a registered `alert-analysis` skill plus a create-an-agent-with-`skill_ids` route already exist, so the Reason phase (FR-5) and the A-1 skill unknown resolve toward reuse. The `@kbn/evals` harness already provides offline datasets, trace/tool-call evaluators, and exponential-backoff retry, with a one-line `evaluate = base.extend(...)` per-suite convention to copy. The greenfield pieces are narrow and specific: the `daybreak` plugin and its experimental flag (FR-12/NFR-2), the FR-7 Proposal/Evidence stores and approval gate, the FR-2 `fetch_runtime_config` reference (external to this repo), and the FR-11 UI panel itself.

## Detailed Findings

### 1. The Workflow engine exists and already expresses the required step shape (FR-1, PD-1, A-2)
The substrate the spike must validate is the shipped `workflows_execution_engine` plugin. It defines the three primitive step types the spike composes: an HTTP-fetch step (`type: kibana.request` accepting `request: { method, path, body, query, headers }` in Dev-Console form), a conditional-guard step (`type: if` with a `condition:` expression over prior step outputs), and an AI-invocation step (`type: ai.agent`, covered in Finding 2). A real, scheduled `streams` workflow already chains a `kibana.request` step directly into an `if` guard and then into `foreach`/`while` loops — i.e. the exact HTTP→guard composition PD-1 wants to prove is already in production use (on a stricter 10-minute schedule than a spike needs). The same shipped YAML also demonstrates engine-level retry (`on-failure: retry` with exponential strategy), relevant to A-4. The runner API (`executeWorkflow`, returning a `workflowExecutionId`) and an integration-test fixture (`WorkflowRunFixture`, which runs an inline-YAML workflow with mocked repositories and exposes an `echo_inference` fake connector for a stub AI step) are both present. A-2 ("does the engine support the step shape") resolves in the engine's favor; PD-1 is confirmatory. The deeper engine internals in this paragraph were established by the PD-1 spike research in this feature (`daybreak-s1-pd1-workflow-engine-spike/research.md`); the HTTP step and shipped composition were re-verified directly for this brief.

### 2. `ai.agent` provides Zod structured output and fails closed (FR-5, FR-6)
The real Reason-phase primitive is the Agent Builder `ai.agent` step type. Its server handler reads a `schema` from the step input, passes `structuredOutput: !!schema` and `outputSchema: schema` into the execution service's `executeAgent`, then reads `round.response.structured_output` as the structured result (and `JSON.stringify`s it into the step output when a schema is set). The handler fails closed in two ways that directly ground FR-6: it throws when no `round_complete` event is received, and the whole step is wrapped in a try/catch that logs `"agentBuilder.runAgent step failed"` and returns an `{ error }` object instead of emitting a verdict. So neither the structured-output path (FR-5) nor the fail-closed output-validation guard (FR-6) needs to be invented — the step enforces "no event → error" and "throw → error result" by construction. (A stricter per-field Zod `safeParse` rejecting malformed-but-present output is not visible in the handler; whether the worker adds its own boundary check is a PD-2 design choice — see Open Questions.)

### 3. A registered `alert-analysis` skill already exists — A-1 resolves toward reuse (A-1, PD-2, NFR-4)
The proposal's day-1 unknown (build vs. reuse a skill for the Reason phase) resolves toward reuse. A real `alert-analysis` skill is defined via `defineSkillType` (`id: 'alert-analysis'`, basePath `skills/security/alerts`) and registered in the security_solution plugin's agent_builder skill registration. Its `getRegistryTools` returns an allowlisted tool set (`security.alerts`, `security.security_labs_search`, `security.entity_risk_score`, plus a focused inline related-alerts tool) — which is exactly NFR-4's "allowlisted tool calls" constraint, already satisfied. The skill's content guides alert triage → related-alert correlation → Security Labs enrichment → entity-risk assessment → disposition; it emits free-form analysis, not a structured verdict object. That nuance matters for FR-5: the structured output schema is a worker-level concern layered on via the `ai.agent` step's `schema` (Finding 2), not something the skill itself produces.

### 4. An agent can be created scoped to a specific skill list (FR-5 binding)
Binding the Reason phase to the alert-analysis skill (without exposing every skill, per NFR-4) is supported by an existing route: the agent create body schema accepts `skill_ids` (limited via a `SKILLS_SCHEMA`), and the handler calls `service.create(request.body)`. This is the concrete mechanism for PD-2's "minimal agent with `skill_ids: ['alert-analysis']`" — no new agent-creation surface is needed, only a create invocation with a one-skill list.

### 5. `@kbn/evals` already provides the offline-dataset + live-trace harness, plus retry (FR-8, FR-9, A-4, PD-3)
The eval harness FR-8/FR-9 require is a shipped, mature package, not greenfield. Its base `evaluate` export is a Scout/Playwright test extended with worker fixtures (`base.extend<{}, EvaluationSpecificWorkerFixtures>`). Within that base:
- **Offline dataset gate (FR-8):** an `evalsClient` talks to the `evals` plugin backend (`/internal/evals/datasets` create/list routes backed by a scores data stream), and `executorClient` exposes `upsertDataset` / `getDatasetByName` over examples carrying `input`/`output`/`metadata`. A golden set of seeded alerts is a dataset; scoring is platform-provided.
- **Trace/tool-call gate (FR-9):** the base wires `traceBasedEvaluators` (tool-call count, input/output/cached tokens, latency) against a `traceEsClient`, plus LLM `criteria`/`correctness`/`groundedness` evaluators — so "assert on both UI state and trace/tool-calls" is supported directly.
- **Connector flakiness (A-4):** the base already wraps `kbnClient` with retries, and a standalone `withRetry` helper provides exponential backoff over 429 / 502-504 / transient-network errors and parses `Retry-After`-style messages. The retry/backoff strategy the proposal lists as an open question is already implemented.
- **Per-suite convention:** every existing suite (workflows, attack-discovery, endpoint, automatic-migrations, observability-ai-assistant, …) is `export const evaluate = base.extend<…>({})` adding its own client fixture. The workflows suite is a one-screenful example. The spike's harness is a new such suite, not a new framework.

### 6. The "regression-flip" gate is a usage pattern over datasets + scoring, not a platform feature (FR-10, A-3)
FR-10/A-3's requirement that a seeded golden-set regression flips a gate green→red has no dedicated platform primitive — but it does not need one. Datasets carry expected `output` and are scored by the executor; a deliberately-broken worker variant that emits a wrong verdict simply fails the dataset's scoring. So the non-vacuity proof is a matter of seeding one dataset example whose expected output the broken variant cannot satisfy, not of building a "flip" assertion. The adversarial seeding itself (choosing a failure mode the broken variant actually exhibits) remains the spike's job and is the real guard against a vacuous gate.

### 7. Scout/Playwright wait-for-state idiom is established for the UI-journey gate (FR-9, A-5, PD-4)
A-5's Playwright-brittleness concern is mitigated by an existing, copyable wait-for-state convention in the Agent Builder Scout UI tests: assertions use `expect(locator).toBeVisible()` and `expect(async () => { … }).toContainText(…)` polling wrappers — never fixed timeouts — matching the project's never-`waitForTimeout` rule. The `@kbn/evals` package also ships `createPlaywrightEvalsConfig`, a Playwright config builder explicitly for offline evals, so the offline dataset gate and the live UI-journey gate share one Scout/Playwright substrate.

### 8. The feature-flag gating pattern is real; the `daybreak` plugin and flag do not (FR-12, NFR-2)
The flag-gating mechanism is grounded: security_solution reads `this.config.experimentalFeatures` at setup/start and threads it through, and `experimentalFeatures: Record<string, boolean>` is the established shape across the security features package. However, an exhaustive repo search (established by the PD-1 spike research in this feature) finds `daybreak` only inside the OpenSpec proposal text — there is no `x-pack/solutions/security/plugins/daybreak/` directory and no `daybreak` key in any plugin config or experimental-features map. On the plugin-and-flag axis the spike is greenfield: it must stand up a new plugin and a new experimental flag rather than gate behind an existing one. (Forward: tasks — whether plugin/flag scaffolding is in-scope for the spike is unresolved; PD-1 raised it.)

### 9. FR-7's Proposal/Evidence stores and approval gate are greenfield (FR-7, PD-2)
A repo-wide search for `ProposalsClient`, `EvidenceClient`, `evaluateReadinessGate`, or `requireReadinessGate` finds matches only inside OpenSpec artifacts — no committed TypeScript source and no compiled `target/types` declarations for evidence/proposals stores in the current tree. The FR-7 Act-phase Proposal/Result record (actor/timestamp/rationale), the auditable store, and the approval-gate-bounded consequential action therefore have no existing implementation to extend; they are authored from the spike's own design. (Discrepancy to resolve: PD-2's design cites `target/types/server/client/{evidence,proposals}/*.d.ts` as a type-shape reference, but this brief's search located none — see Open Questions.)

### 10. `fetch_runtime_config` is external to this repo (FR-2)
The proposal's "What Changes" says Setup loads per-space runtime config via "a config-fetch step mirroring `fetch_runtime_config`." No `fetch_runtime_config` / `fetchRuntimeConfig` symbol exists anywhere in this repo — the only references are in the OpenSpec text. "The source workflow" James's 9.5 design derives from is not in this repository. The spike's Setup phase therefore defines its own config-fetch step shape (a `kibana.request` to a config endpoint, per Finding 1) rather than mirroring an in-repo function.

### 11. The throughline UI prototype referenced for context is not in this repo (FR-11, PD-4 context)
The operator description references a throughline prototype (`renderWatchesPage`, `renderWatchDetail`, `renderWorkflowsPage`) at `docs-site/prototype/throughline-app.js`. A repo-wide search finds those symbols only inside OpenSpec text — the prototype lives in the external project-daybreak repo, not here. For this spike's narrower FR-11 claim ("a real Kibana UI route/panel showing alert input, phase progress, Proposal, and evidence, backed by spike data"), Kibana route/panel registration is a well-trodden pattern (every plugin under `*/server/routes` registers routes in `start()`), but the host `daybreak` plugin and its panel do not yet exist (Finding 8), so the UI surface is greenfield on the plugin axis.
