WHY · The problem ARGUS is built for
A
ARGUS

The threat model is shifting.

Anthropic's "Mythos era" adversary is not a scaled-up human attacker. It's a frontier-capability reasoner operating at machine speed.
P1 · Time compression

0-day exploit lifecycle collapses from months to hours. SOCs that measure MTTR in days lose.

P2 · Variant explosion

N polymorphs per CVE. Static detections decay silently — the SOC finds out via an intrusion, not a metric.

P3 · Agentic chain

Goal-directed, multi-step, tool-using. Not an exploit — a plan, executed autonomously.

P4 · Capability asymmetry

Frontier reasoner vs. fixed-function SOC. The defender runs out of hours before the attacker runs out of ideas.

The static-rule problem

A detection rule that scored precision=0.92, recall=0.86 at M2.1 deploy time can quietly drift to precision=0.61 in four weeks as the adversary adapts.

ARGUS is the answer: a detection & response surface that adapts on its own, under governance, at the same clock speed as the adversary.

ARGUS

A
ARGUS

Real adversarial inputs for the eval gate.

ARGUS doesn't grade itself against fixtures. The simulator permutes axes to mimic how a Mythos adversary iterates.
Two-workflow handshake
Step 1 · Arm preset

soc-argus-arm-mythos-preset.yaml

Operator (or automation) arms a difficulty level + technique. Indexes a pending attack-command.

Step 2 · Emit variant

soc-argus-frontier-simulator.yaml

When preset is armed, emits a polymorphic variant into .soc-eval-corpus-* via _reindex + inline Painless, preserving nested ECS.

Why polymorphism matters

The simulator doesn't replay fixtures. It permutes four axes — loader, delivery, privilege, stealth — to mimic how a real Mythos adversary iterates per tenant, per host, per hour.

The variant bank grows organically. M2.1 keeps a coverage map, so if the simulator starts emitting on an axis the current rule doesn't cover, the coverage number drops — and drift monitor sees it.

GOVERNANCE · Trust-policy matrix
A
ARGUS

Tier × blast-radius × door-class.

The matrix that decides who can auto-apply what. Spec: @kbn/argus-trust-policy · 27 tests incl. 160-combo exhaustive matrix + YAML⇔TS drift detector.
Input 1

Actor trust tier

  • frontier — full auto-apply
  • probationary — narrow blast only
  • quarantined — review required
  • unproven — new actor, caps at narrow
Input 2

Blast radius

  • narrow — single rule, 1 tenant
  • wide — multi-tenant, 1 host class
  • global — platform-wide

Computed from expected_impact.hosts / tenants / rules.

Input 3

Door class

  • two_way — reversible (rule_create default)
  • one_way — irreversible in practice (kill-switch, tenant isolation)

One-way doors always route to review regardless of tier.

Decision
if door_class == "one_way":
    pending_review   // irreversible
elif tier == "quarantined":
    pending_review   // frozen actor
elif blast_tier > tier_cap:
    pending_review   // over budget
else:
    auto_apply_ready // through the gate

Verdict rubric
safe

Projected hits land cleanly on known-bad. Applier proceeds.

noisy

High FP signature against historical traffic → block, re-route to synthesis for tightening.

silent

Rule never fired in 7d of traffic → block, advisory gets re-evaluated (does the TTP still exist?).

dangerous

Projected hits on core infra or high-priv services → block, escalate to human review.

A
ARGUS

Every auto-apply is a canary, not a cutover.

Spec: soc-post-apply-observer.yaml · 2-min tick · regression gate = (spike ∨ silence) ∧ tp_drop · rollback rides the same applier path as any other mutation.
What a canary is today
applier apply rule
      │   // writes `.soc-snapshots` doc
      │   // with `before` state + parent_rec_id
      ▼
observation window  =  15m
baseline window         =  60m pre-apply
cooldown between ticks  =  5m
      │
      ▼
soc-post-apply-observer · every 2m
  • spike     post > 3× pre
  • silence   post == 0 && pre > 0
  • tp_drop   pre_tp > 0 && post_tp == 0
      │
      ▼
regression = (spike ∨ silence) ∧ tp_drop
      │
      ├── clean          → snapshot closed · rec stays applied
      ├── inconclusive   → empty baseline · keep observing
      └── regression     → emit rollback_mutation_intent
                           applier reverts to before
                           parent rec flips to rolled_back
Why this is already strong
  • One applier path — rollback is just another mutation_intent, so the audit story is uniform.
  • No false regressions — requires both a volume anomaly and a TP collapse; empty baselines degrade to inconclusive.
  • Closed loop on disk — every tick writes to .soc-post-apply-observations + .soc-autonomy-decisions; dashboards reconstruct the decision.
To go production-ready
1 · Staged fleet rollout

Today every apply goes to 100 % of hosts at once. Production needs 1 % → 10 % → 50 % → 100 % stages with a gate evaluation between each, using Agent tag / space / tier selectors. Abort on first stage that regresses — the blast radius stays bounded to the smallest cohort.

2 · Statistical significance gating

The 15-min window is time-bounded, not sample-bounded. Promote when N ≥ 30 matched events and the 95 % CI on FP-rate lies below the SLO — not when the clock rings. For low-traffic rules, extend the window automatically.

3 · Versioned, atomic rollback

Replace "re-apply the before doc" with an immutable rule-bundle keyed by content hash. Rollback = switch the active pointer to v(n-1), tamper-evident, race-free. Adds a global kill-switch that can disable a rule-set fleet-wide in < 30 s.

4 · Per-tier SLOs & alert budgets

The 3× spike / 70 % TP-drop thresholds are hard-coded constants. Replace with per-rule SLOs (crown-jewel EDR ≠ noisy auth rule) + a global alert-volume budget; refuse to promote if the projected volume pushes the fleet past its error budget.

5 · Blast-radius simulator + HITL escalation

Pre-promotion, replay the rule against the last 24 h of live telemetry on a read-only mirror to predict the alert storm. Borderline verdicts (inconclusive, near-threshold) pause at 25 % and page on-call via the detection-engineer escalation queue instead of auto-rolling forward.

6 · Signed audit + crown-jewel lockout

Every stage transition gets a signed entry in a tamper-evident log (hash-chained to the previous). During active incidents or on crown-jewel assets, auto-apply is disabled — the applier queues the intent behind a human gate regardless of backtest verdict.

PHASE 3 · Drift detection
A
ARGUS

Notice when the world moves.

The loop that catches silent decay before it becomes an intrusion. No LLM — just a smoothed rolling average + thresholds.
Detection math
// per rule, last 30 days, ≥3 runs
// EMA = exponential moving average — a smoothed trend where
// the newest run counts most and older runs fade out.
// α=0.3 means the latest run gets ~30% of the weight.
ema_precision = EMA(precision, α=0.3)
baseline      = median(last 7 runs before current)
Δ             = ema_precision - baseline

drift_significant =
  |Δ| ≥ 0.08                                       // absolute drop
  OR
  (Δ ≤ -0.04 AND variant_coverage_delta ≤ -0.10)

// analogous for actor trust from .soc-actor-trust-tiers
// + reasoning_trace_quality (M2.5, 24h window)
Effect

Files a mutation_intent with argus.origin: drift_detected, status: eval_requested. Existing M2.1 cascade re-scores against the current corpus on the next tick.

48h cooldown per target to avoid flapping.

Why deterministic

A smoothed rolling average, then a threshold.

We track each rule's precision over time using an exponential moving average (EMA) — a rolling average that weights the most recent run highest and lets older runs fade out. When the smoothed trend drops past a threshold, ARGUS files a drift intent.

One knob — α = 0.3 (how much weight the latest run gets) — controls the whole detector. Reviewable, calibrated, debuggable. No LLM, no black box.

Two streams, one workflow

Rule drift + actor drift

  • Rule drift — score trajectory per rule_id
  • Actor drift — trust trajectory + reasoning quality per actor_id

Single origin: drift_detected with kind discriminator — keeps the applier path uniform.

PHASE 3 · Playbook learning loop
A
ARGUS

ARGUS learns which step actually works.

Per (technique, playbook_step) pair, correlate outcomes and remap under-performers — adversary-proof by construction.
Correlator
// per (technique, playbook_step), rolling window

success_rate  = successful_outcomes / total_outcomes
rollback_rate = rollbacks          / total_applies

if success_rate < threshold OR
   rollback_rate > threshold:

  // file a remap intent
  candidate = rank_from(
    "argus/technique-playbook-mapping.json",
    by=historical_success_on_adjacent
  )

  emit mutation_intent(
    origin="playbook_remap",
    payload={
      from: playbook_step,
      to:   candidate,
      technique: technique
    }
  )
Adversary-proofing
Gate 1 · tier

Frontier-tier outcomes only

Quarantined actors can't poison the loop by deliberately failing — their outcomes are filtered out of the correlator.

Gate 2 · sample

Minimum sample size

A single outcome can't flip a playbook step. The threshold requires enough evidence to be statistically distinguishable from noise.

Mapping source

argus/technique-playbook-mapping.json

Static, checked-in, human-reviewed. Candidates are ranked by historical success on adjacent techniques (same tactic, same kill-chain stage).

Q&A · Anticipated questions
A
ARGUS

Questions & answers.

Product
How do we know this works?
Live-runtime validation on a real Kibana cluster (completed=8, failed=0), 187+ unit tests, YAML⇔TS drift detectors, per-module proof docs under docs/argus/proof/.
What's the risk of autonomous mis-action?
One-way doors force review. Blast-radius tiers cap what a probationary actor can touch. Every action is shadow-executed via the backtester. Rollback is the default response to a dangerous verdict.
Competitive positioning?
Our differentiator is the governance spine — blast-radius × tier × door-class × backtest — something the “ship it autonomously” entrants don't have.
Engineering
Where is the state machine?
There isn't one. Every workflow is a reconciler against ES docs. status fields on .soc-recommendations are the state. A crashed workflow cannot corrupt state it doesn't own.
What if the LLM hallucinates a rule?
The eval gate catches it — a hallucinated rule fails variant-axis coverage and/or precision. The rec stays pending, the trace captures the failure, and the watchdog marks the actor's confidence down.
How do you prevent the eval corpus from being gamed?
ATT&CK ER7 external corpus — ARGUS is scored against a bank it didn't author. Phase-3 learning is gated to frontier-tier outcomes so a quarantined actor can't poison the loop.
