Data Flow

How data moves between Argus steps
Autonomous · Resilient · Guardian for · Unified · Security
Argus is not a pipeline; it's a closed loop over Elasticsearch. Every step reads from and writes to .soc-* indices, stamps an OTLP reasoning trace, and hands the next agent a document — never a function call. This deck walks the data layer by layer: Sense → Hypothesize → Validate → Act → Govern, and the feedback path that closes the loop.

05 · HYPOTHESIZE
A
ARGUS · DATA FLOW

Step 2 · Hypothesize

Planner-class agents read the sense layer and write two artifacts: a recommendation (what to do) and a mutation intent (the draft rule itself, with justification).

input → processing

What each agent reads

  • Triage · ECS alerts + .soc-telemetry-signals → classification + disposition
  • DetEng · .soc-cve-advisories + corpus + patterns → rule draft
  • Hunter · endpoint events + corpus → hunt query + gap
  • Gap analyzer · .soc-threat-profiles × corpus → .soc-coverage-gaps
  • Meta agent · hunter + gap + DetEng → Pareto candidates
output → next stage

What each agent writes

Two documents travel forward together, joined by mutation_intent_id:

  • .soc-recommendations — proposal, confidence, frontier/dominated flag, procedure clusters
  • .soc-mutation-intents — draft rule, query, severity, MITRE, justification

Both carry the same trace_id, so any downstream viewer (flyout, decision graph) can resolve the full reasoning chain.

Canonical mutation-intent payload
{
  "@timestamp": "2026-04-22T13:29:09.200Z",
  "mutation_intent_id": "mut-e2d-dnsc2",
  "trace_id": "5b1e...a7",                                 // joins .soc-reasoning-trace
  "status": "queued_for_eval",
  "actor": { "id": "soc-deteng-agent", "trust_tier": "probationary" },
  "draft_rule": {
    "rule_id": "argus.command-and-control.t1071_004.argus-adv-dns-c2-2026-04",
    "severity": "medium",
    "language": "kuery",
    "query":    "event.dataset:\"dns\" and dns.question.type:(\"TXT\" or \"NULL\") ...",
    "mitre":    [{ "technique_id": "T1071.004", "tactic": "command-and-control" }],
    "justification": { "observable_signals": ["dns_txt", "non_rfc1918_resolver"] }
  }
}
06 · VALIDATE
A
ARGUS · DATA FLOW

Step 3 · Validate

A mutation intent can't reach Act until three validators write gate decisions back onto it. Failed gates stay in the index — they are the most important data in the loop (negative evidence).

03a · BACKTEST

Replay against history

Reads the draft query from the intent, executes it against .alerts-security.* over the last 30 d.

Writes .soc-backtest-results with windows_tested, true_positives, false_positives, gate_decision.

03b · EVAL

@kbn/evals vertical

Runs the rule against logs-argus_eval.scenarios-* — Caldera + synthesized mutation scenarios — via the rule preview API.

Writes .soc-detection-eval-runs with scores.precision, scores.recall, variant_coverage, mutation_robust.

03c · GATE + TRUST

Regression + trust scorer

Regression gate re-runs the existing live rules against the draft's corpus — blocks if any existing rule regresses.

Trust scorer averages actor-level success rate and stamps actor.trust_tier back onto the intent.

Write-back: the gate decision lands on the intent
// POST .soc-mutation-intents/_update/mut-e2d-dnsc2
{
  "doc": {
    "governance_gate": {
      "status": "pass",              // or "block" — this is what the applier reads
      "reason": "precision 0.94, recall 0.82, 2 FP in 30d",
      "eval_run_id": "eval-mut-e2d-dnsc2-0",
      "backtest_id": "bt-mut-e2d-dnsc2-0"
    },
    "status": "gated_pass",
    "actor": { "trust_tier": "probationary" }  // stays probationary until post-apply observer confirms
  }
}

08 · GOVERN
A
ARGUS · DATA FLOW

Step 5 · Govern & Feedback

Governance isn't a gate before an action — it reads the outcomes layer continuously and writes back signals that reshape the next hypothesis.

Outcomes → signals

What gets read

  • .soc-outcomes — per-rule TP/FP, rollback events
  • .soc-reasoning-trace — per-decision latency and tool use
  • .soc-autonomy-decisions — volume, confidence spread
  • .soc-backtest-results + .soc-detection-eval-runs — trending quality
Signals → write-back

What governance writes

  • .soc-actor-trust-tiers — per-agent trust (blocks apply)
  • .soc-quality-score-history — per-rule trajectory
  • .soc-kill-switch — global halt when budgets tripped
  • .soc-audit-trail — every console-originated op
  • .soc-decision-graph — joined trace + lineage
How the loop closes
rising tier

Trust up → broader scope

An agent whose intents pass post-apply observation cleanly for N applies is promoted from probationary to trusted. The applier starts accepting its intents at lower confidence thresholds.

falling tier

FP spike → cooldown

A rolled-back outcome bumps the actor's tier down, widens the regression window for its next intent, and forces human approval. Same document trail, different edge weights.

Corpus update

Good intents → corpus

Outcomes with rolled_back: false and high variant coverage are promoted into .soc-detection-corpus, so the next DetEng agent sees them as patterns to generalise, not one-offs.

09 · TRACE · OTLP SPINE
A
ARGUS · DATA FLOW

The trace is the audit log

Every step emits OTLP spans. A single trace_id binds every document on the path — so the Console can reconstruct why any rule exists, back to the first telemetry event.

Span schema

One row per agent / tool call

{
  "@timestamp": "2026-04-22T13:29:09.200Z",
  "trace_id": "5b1e...a7",
  "span_id": "3c09",
  "parent_span_id": "0c4a",
  "agent": "soc-deteng-agent",
  "tool": "rule_preview",
  "input": { "query": "event.dataset:dns..." },
  "output": { "precision": 0.94, "recall": 0.82 },
  "duration_ms": 412
}
Joining the graph

Every doc carries trace_id

Because trace_id is stamped on every hop (.soc-recommendations, .soc-mutation-intents, .soc-detection-eval-runs, .soc-outcomes, .soc-autonomy-decisions), a single ES join reconstructs the graph.

Decision-graph builder reads all five indices, emits typed nodes/edges to .soc-decision-graph, and the Console's Decision Graph tab renders it directly.

Invariant A stage with no span can't write a doc. Any orphan triggers an audit_trail entry and blocks further progress for that mutation_intent_id.

11 · INVARIANTS
A
ARGUS · DATA FLOW

Four invariants the loop enforces

The data layer doesn't just record what happened — it makes certain outcomes impossible to reach.

I1 · No apply without a span

Trace binds every hop

Applier refuses any intent whose most recent span is older than the governance gate's decided_at. Lost the trace → blocked.

I2 · No evidence-free gate

Backtest + eval both required

The applier reads governance_gate.eval_run_id and backtest_id before acting. Either missing → rejected with reason: "insufficient-evidence".

I3 · Every apply is reversible

Pre-state snapshot is mandatory

.soc-autonomy-decisions rejects docs without pre_state. Observer uses it as the rollback target verbatim — no state reconstruction at recovery time.

I4 · Kill-switch overrides everything

Singleton read on every apply

Applier reads .soc-kill-switch/_doc/global before every rule write. If enabled: true, every op becomes a no-op that still writes an audit_trail row.

the payoff

Why this shape?

Every invariant above is a query, not a code path. Governance, audit, and rollback fall out of the index contract — they aren't middleware that can be bypassed. Drop a new agent into Agent Builder, point it at the same indices with the same spans, and the loop absorbs it without changing a single line of the applier or observer.

A

Documents, not RPCs.

The pipeline is the index set.
Swap any agent for a better one; add a validator; pause the applier; replay yesterday's decisions against today's corpus — none of it breaks the contract, because the contract is a dozen Elasticsearch indices joined by trace_id.

That is what makes Argus composable, auditable, and resilient against a frontier adversary.
