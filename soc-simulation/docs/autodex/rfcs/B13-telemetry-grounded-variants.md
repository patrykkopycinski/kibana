# RFC B13 — Telemetry-grounded variant generation

> **Status:** Pure-logic abstraction implemented (2026-05-05).
> Server-side reasoning-trace adapter pending — see §5.
> **Owner:** AutoDEX productionisation track.
> **Closes (partial):** vision-doc requirement **1.4.4**
> ("Variant bank grounded in real attack telemetry").
> **Tracked by:** B13 in [`conformance-matrix.md`](../conformance-matrix.md) §7.

---

## 1. Why this gap matters

Every variant the M2.1 detection-eval gate scores is generated by the
`VariantProvider` chain:

- `deterministic` — hand-authored axis library (`generate_variants.ts`).
- `scripted-llm` — hashed-prompt seeded fake (`llm_variant_provider.ts`).
- `connector` — real LLM via `@kbn/argus-inference-variant-provider`.

All three sources of variants are *imagined* — by an author or by a model.
The polymorphism surface is frozen at imagine time, which means:

1. The eval gate can only grade rules on shapes we already thought of.
2. Real-world attacker behaviour observed in production never feeds back
   into corpus generation. A new BITSAdmin variant Caldera replays in
   tomorrow's attack-emulation run will not influence the eval gate
   scoring of any rule we synthesise the day after.
3. The "self-improving" claim of AutoDEX has a quiet asterisk on it.

Vision-doc requirement 1.4.4 specifically calls out *grounding* the variant
bank in real attack telemetry. B13 closes that loop.

## 2. Design

A new abstraction, `TelemetryVariantSource`, sits alongside the existing
`VariantProvider`. The source produces samples drawn from observed
telemetry; a `createTelemetryGroundedProvider({ source, fallback })`
factory wraps the source into a `VariantProvider` so the existing
orchestrator (`generateLlmVariants`, `synthesizeOne`, the workflow step)
sees no API change.

```
┌─────────────────────────────────────┐
│ generateLlmVariants                 │
│  for each (axis, platform):         │
│    provider.generate(...)  ─────────┼──┐
└─────────────────────────────────────┘  │
                                          ▼
                       ┌──────────────────────────────────┐
                       │ createTelemetryGroundedProvider  │
                       │  1. source.fetch(...)            │
                       │  2. validateLlmVariant(sample)   │
                       │  3. shortfall → fallback.generate│
                       └──────────────────────────────────┘
                          │                       │
                ┌─────────▼──────────┐  ┌────────▼─────────┐
                │ TelemetryVariant   │  │  fallback        │
                │ Source.fetch       │  │  (scripted-llm   │
                │   (recorded data)  │  │   or connector)  │
                └────────────────────┘  └──────────────────┘
```

### 2.1 Source contract

```ts
interface TelemetrySample {
  sample_id: string;
  process_name: string;
  process_executable: string;
  command_line: string;
  parent_name: string;
  parent_executable: string;
  source_metadata?: Readonly<Record<string, string | number | boolean>>;
}

interface TelemetryVariantSource {
  fetch(input: TelemetryVariantSourceInput): Promise<readonly TelemetrySample[]>;
}
```

The source returns at most `input.budget` samples per (axis, platform). The
orchestrator validates each sample using the existing
`validateLlmVariant` gate (golden-set blocklist + axis-marker invariants
+ platform binary allowlist). Validation rejections are surfaced via an
optional `on_sample_rejected` hook so per-source quality metrics can be
captured without lacing them into the main reasoning-trace sink.

### 2.2 Provenance and trace shape

Accepted samples land in the corpus tagged with a
`${source_name}:${sample_id}` rationale (default source_name is
`'telemetry-grounded'`; server-side adapters typically pass `'reasoning-trace'`,
`'caldera-replay'`, etc.). This lets:

- The reasoning-trace sink colour-code the corpus by provenance.
- Downstream observability ("how much of this corpus is grounded vs
  imagined") render directly off the rationale prefix.
- Rejected samples surface their `sample_id`, `axis`, `platform`,
  `advisory_id`, and rejection reasons so source operators can
  diagnose what the validator is throwing away.

### 2.3 Fallback semantics

`createTelemetryGroundedProvider` ALWAYS returns exactly `input.budget`
candidates — the existing `generateLlmVariants` orchestrator throws when a
provider under-delivers, and the eval gate assumes every (axis, platform)
contributes a full budget. So:

- If telemetry returns 0 valid samples → 100% fallback.
- If telemetry returns 3 valid samples for a budget-of-5 → 3 telemetry +
  2 fallback.
- If the fallback itself under-delivers → the orchestrator throws, surfacing
  the broken contract instead of silently shipping a smaller corpus.

Telemetry samples come first in the output; fallback fills the tail. This
keeps the trace sink's "first N grounded" assertion clean on the consumer
side.

## 3. Determinism

The orchestrator preserves determinism when both the source and fallback
are deterministic. The bundled `inMemoryTelemetryVariantSource` is
deterministic (it filters and truncates an authored entry list); the
default scripted-llm fallback is deterministic (mulberry32 + hashed
prompt seed); a connector-backed fallback is non-deterministic by design
but acceptable when calibrated against M2.1 fixtures.

Tests cover the determinism contract end-to-end:

```ts
const out1 = await provider.generate(input);
const out2 = await provider.generate(input);
expect(out1).toEqual(out2);
```

## 5. What does NOT ship today (deliberately deferred)

The pure-logic abstraction is shippable on its own — it lets server-side
adapters, fixture-driven evals, and offline replay all use grounded
variant generation today. Two specific adapters are deferred:

### 5.1 `reasoningTraceVariantSource` — `.soc-reasoning-trace` adapter

The reasoning-trace index (`schemas/soc-reasoning-trace.json`) is structured
around per-step trace events. Variant generation events are emitted via
the `VariantTraceSink` callback in `llm_variant_provider.ts` and are NOT
currently persisted with structured per-variant fields — the index has no
`argus.variant.{process.*, command_line}` mapping.

Two ways to fix that:

1. **Schema migration.** Add `argus.variant` nested mapping to
   `.soc-reasoning-trace`. Existing producers (the trace sink wired into
   `generateLlmVariants`) populate the new field whenever they emit a
   `VariantTraceEvent`. The adapter then queries
   `argus.variant.accepted=true` rows and maps them to `TelemetrySample`s.
   - Pro: reuses the existing trace pipeline, no new index.
   - Con: schema migration to a permanent-retention index.

2. **New `.soc-variant-corpus` index.** Add a typed index that the trace
   sink writes to alongside `.soc-reasoning-trace`. Adapter queries
   `.soc-variant-corpus` directly.
   - Pro: dedicated schema, narrower mapping, no churn on the
     reasoning-trace contract.
   - Con: new index, new template, new ILM policy.

Option 2 is the cleaner path; option 1 is faster. The decision blocks on
[#TBD] once the productionisation plan slot for B13's adapter lands.

### 5.2 `calderaReplayVariantSource` — Caldera attack-emulation adapter

The `elastic-attack-emulation` plugin records Caldera replay traces.
Wrapping those traces as a `TelemetryVariantSource` is a natural
follow-up — the replay output already carries process/parent/command-line
fields. Pending the adapter spec; the plugin team owns the trace shape.

## 6. Risk

- **Poisoned telemetry is real.** A real-attacker-controlled environment
  could emit `process.command_line` strings designed to drift the eval
  gate's blocklist. This is why every sample passes `validateLlmVariant` —
  the same gate that catches LLM hallucinations of real C2 hostnames also
  catches real-but-poisoning telemetry.
- **Determinism vs freshness.** A real source returns the latest samples,
  which mutate as new telemetry lands. Synthesis runs that need
  reproducibility (e.g. M2.1 fixtures) MUST scope the source by a fixed
  window or sort-key; the in-memory source enforces this trivially, the
  reasoning-trace adapter will require operator-supplied snapshot timestamps.
- **Provenance leak.** `source_metadata` ships into the rationale field.
  Adapters MUST scrub anything that could leak attacker IPs / domain
  reputation hashes / customer identifiers — the same treatment any data
  contract owes for write-side governance.

## 7. Out of scope for this RFC

- **Per-source budget tuning** ("80% telemetry, 20% LLM diversity"). The
  current orchestrator is "telemetry first, LLM fills the gap" which is the
  defensible default. A `max_telemetry_fraction` knob can land later if
  M2.1 evals show the corpus over-converges on observed shapes.
- **Sample dedup.** Sources are responsible for returning distinct samples.
  An orchestrator-level dedup-on-`sample_id` would mask source bugs.
- **Cross-corpus telemetry sharing** ("samples from corpus A used for
  rule B"). Out of scope; the source `corpus_id` parameter is forwarded
  for adapter scoping but the orchestrator does not enforce a policy.
