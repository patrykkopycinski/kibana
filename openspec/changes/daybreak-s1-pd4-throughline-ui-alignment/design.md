# Design

## Approach

PD-4 ports the Throughline (NotDaybreak) prototype into a new greenfield `public/` layer of the daybreak plugin, rendering real PD-2 worker output — Evidence and Proposals — through prototype-faithful React components, gated behind a default-off experimental flag (FR-11, FR-12, NFR-2). The architecture is a React application over a thin HTTP client that reads the existing PD-2 store contracts; no server business logic is invented. The component decomposition mirrors the prototype's render-function structure one-to-one (shell → rail/nav/stage/composer; thread → stream/msg/spine/inspector; brief; gate) so each ported surface is independently diffable against the prototype, which the proposal requires before each port. Approval actions call the existing server-side readiness gate rather than replicating its rule client-side (FR-7, A-3).

Three premises in the proposal do not match the repository, and the design treats each as a hard precondition rather than papering over it. First, as research.md establishes in §1, the Throughline prototype is absent from the working tree and all git history, so every prototype symbol the proposal cites (`TL_CSS`, `renderApp`, `renderInspector`, `briefView`, `renderSuggest`, `STATUS_DOT`, `SEV`, `gate-yes`/`gate-ic`, …) is unverifiable until the prototype is vendored into the repo. Second, the feature worktree HEAD (`ec14270513eb`) contains no daybreak code at all; PD-1/PD-2 live only on `origin/daybreak-spike` (tip `2cbad6ad0e78`, corrected 2026-07-09 from the stale `33a054f1afad` after 3 unpushed worker-mirror commits were reconciled to origin — see research.md §2), so the spike branch must be merged before any UI work. Third, the daybreak plugin is server-only — `"browser": false, "server": true` (`x-pack/solutions/security/plugins/daybreak/kibana.jsonc:12-13`) with no `public/` directory, no application route, and no HTTP API exposing the stores (research.md §3, §4, §6; verified: no `router.`/`createRouter`/`http.` usage anywhere in `server/`). PD-4 therefore builds the `public/` layer, the app route, and a thin transport API fresh.

The one place PD-4 touches server runtime is adding HTTP routes that wrap the already-implemented `EvidenceClient` and `ProposalClient` (`server/client/evidence/client.ts:22`, `server/client/proposals/client.ts:22`) as pure pass-through transport — the proposal's "real data wiring (not mocked)" requires an API that research.md §6 proves does not yet exist. The gate-approval flow calls `ProposalClient.transitionStatus(id, 'approved')` (`server/client/proposals/client.ts:34`, impl at `:182`), which already enforces `requireReadinessGate` (`server/client/proposals/gate.ts:98`) internally (`client.ts:189`), so fail-closed approval is a server property the UI inherits, not one it re-implements. The "existing daybreak experimental flag" the proposal and NFR-2 reference is the verified config boolean `xpack.daybreak.enabled` (`common/config.ts:17`, whose comment at `:13-14` calls it "an experimental feature flag") — not a platform `experimentalFeatures` entry, which does not exist anywhere in the plugin (research.md §4).

## Components

- **`public/plugin.ts` (client plugin)** — new. Flips the manifest to `browser: true` and registers the daybreak Kibana application route, gated on the enabled flag via `appUpdater` so the nav entry is hidden when `xpack.daybreak.enabled` is false (NFR-2). Mounts the React tree. The server `setup()`/`start()` already early-return when `!this.config.enabled` (`server/plugin.ts:33`, `:43`); PD-4 surfaces that same boolean to the client so the browser gate and the server gate are one switch.
- **`public/application/theme.ts`** — the design-token system. Ports the prototype's CSS custom-property layer (neutrals, semantic, thread-type, shape) and the `applyAccent`/`applyTheme`/`applyRadius`/`applyShadow` overrides into an Emotion theme consumed by the React tree; maps tokens 1:1 onto EUI theme tokens where equivalents exist and records the deltas here otherwise. Supports light and dark, defaulting to the prototype's dark build. Exact token values are pending prototype intake (see Failure Modes).
- **`public/application/components/shell/`** — application shell: rail, thread list/nav, main stage, composer (mirrors prototype `TL_SHELL` / `renderRail` / `renderNav` / `renderStage`). The plugin's top-level React route component.
- **`public/application/components/thread/`** — conversation view: message bubbles, tool-call cards, evidence/timeline/narrative/MITRE panels, status dots, severity pills, and the inspector (mirrors `renderStream` / `renderMsg` / `renderSpine` / `renderObjectApp` / `renderInspector`). Thread types case / investigation / hunt / incident / chat.
- **`public/application/components/brief/`** — operator landing page: open threads, awaiting-review items, suggested next actions, plus radar-page and chat-dock docking logic (mirrors `briefView` / `syncChatDock`).
- **`public/application/components/gate/`** — permission popover and approval gate (mirrors `renderSuggest` / `#permPop`): the "read & gather auto-runs / assemble & draft proposed as a diff / world-changing actions need approval" model. Approval actions POST to the transition route and render the server's `GateFailure` when blocked.
- **`public/application/api/`** — typed HTTP client and data hooks (`useEvidence`, `useProposals`, `useProposalTransition`, `useProposalEvidenceRef`) consuming the transport routes below. The transition hook exposes `missingRequirements` to the gate UI so a blocked approval states *why* (FR-7).
- **`server/http_routes/` (new)** — thin pass-through routes wrapping `EvidenceClient`/`ProposalClient`; no business logic. The `/proposals/{id}/transition` route wraps `transitionStatus` (`client.ts:34`) and maps `ReadinessGateError` (`gate.ts:35`) to a `422` carrying `missingRequirements`. Routes are registered in `start()` (`server/plugin.ts:42`) only when `config.enabled`, constructing space-scoped clients per request (the clients are space-scoped — `evidence/client.ts:56`, `proposals/client.ts:65`, filtered via `createSpaceFilter` at `evidence/client.ts:53` / `proposals/client.ts:62`).
- **`common/types/` (lifted)** — pure type declarations (`ProposalProperties`, `EvidenceProperties`, `ProposalStatus`, `GateResult`, `MissingRequirement`, the kind/provenance/stance/sensitivityLabel unions) moved from `server/client/{proposals,evidence}/` to `common/` so the `public/` bundle and the server share one contract instead of the public side re-declaring types (drift risk). Type-only move; no runtime change to PD-2.
- **UI-journey eval (reuses PD-3)** — a Playwright spec layered on the PD-3 `@kbn/evals` primitives (FR-9): app loads → brief renders → thread opens → Evidence renders in inspector → a Proposal gate is approved and applied. Assertions use explicit wait-for-state, never fixed timeouts (A-5, per the PD-4 reconciliation row). See Failure Modes for the PD-3-not-yet-built sequencing risk.

## Data Model

All PD-2 contract citations below are on `origin/daybreak-spike` (research.md §2, §5); they are not present on the feature worktree HEAD. The UI renders two real PD-2 contracts and one gate contract. These are the only verified, citable shapes; the prototype's own UI symbols (`SEV`, `STATUS_DOT`, `STATUS_RANK`, `gate-yes`/`gate-ic`) cannot be confirmed against the missing prototype and are mapped conceptually below pending intake.

**Proposal** (`server/client/proposals/types.ts`) — the Act-phase output (FR-7, hook 6):
- `ProposalStatus` (`types.ts:11`) — `'new' | 'needs-evidence' | 'approved' | 'modified' | 'dismissed' | 'escalated' | 'deferred'` (`:12-18`).
- `ProposalProperties` (`types.ts:34`): `sourceWatch?` (`:37`), `capability` (`:38`), `severity: 'low'|'medium'|'high'|'critical'` (`:39`), `confidence: number` (`:40`), `status: ProposalStatus` (`:41`), `owner?` (`:42`), `createdAt` (`:43`), `recommendation?` (`:44`), `evidenceRefs: string[]` (`:45`), `expectedImpact?` (`:46`), `riskCaveats?: string[]` (`:47`), `approvalRequirement?: 'manual'|'automatic'` (`:48`), `decisionHistory: DecisionHistoryEntry[]` (`:49`), `space?` (`:50`).
- `DecisionHistoryEntry` (`types.ts:23`) — `fromStatus`/`toStatus` (`:24-25`), `actor?`/`reason?`/`timestamp` (`:26-28`): the auditable trail the gate UI appends on each transition.
- `ProposalDocument = Pick<GetResponse<ProposalProperties>, '_source'|'_id'>` (`types.ts:54`).

**Evidence** (`server/client/evidence/storage.ts` + `types.ts`) — the Enrich-phase output (FR-4, hook 3):
- `EvidenceProperties` (`storage.ts:37`): `id` (`:38`), `kind: 'alert'|'event'|'entity'|'timeline'|'query'|'assumption'|'external'` (`:39`), `sourceRef?` (`:40`), `summary` (`:41`), `provenance: 'capability'|'skillVersion'|'tool'` (`:42`), `confidence: number` (`:43`), `stance: 'for'|'against'` (`:44`), `limitations?` (`:45`), `sensitivityLabel: 'public'|'internal'|'restricted'` (`:46`), `createdAt` (`:47`), `space?` (`:48`). Indexed as `.daybreak-evidence` (`storage.ts:13`).
- `EvidenceDocument = Pick<GetResponse<EvidenceProperties>, '_source'|'_id'>` (`types.ts:12`).

**Readiness gate** (`server/client/proposals/gate.ts`) — hook 7, fail-closed (FR-7, A-3):
- `GateResult` (`gate.ts:28`) = `{ approved: true; proposalId: string }` (`:29`) | `{ approved: false; failure: GateFailure }` (`:30`).
- `GateFailure.missingRequirements: MissingRequirement[]` (`gate.ts:22`), `MissingRequirement = 'evidence' | 'recommendation'` (`gate.ts:11`).
- `evaluateReadinessGate(proposal, targetStatus)` (`gate.ts:62`): any target other than `'approved'` passes (`:66-67`); transition to `'approved'` fails closed unless `evidenceRefs` is non-empty (`:47`) **and** `recommendation` is non-empty (`:50`). `requireReadinessGate` (`gate.ts:98`) throws `ReadinessGateError` (`:35`, `:104`) on failure.

**HTTP wire format** (new transport routes, all `internal/daybreak/...`, returning the typed resource directly):

The only derived view is the gate UI's decision to show an explicit approval control when `approvalRequirement === 'manual'` (`types.ts:48`) versus auto-applying when `'automatic'`.

## Failure Modes

- **Prototype absent from the repo (research.md §1).** Every prototype symbol and `~line` citation is unverifiable; porting cannot begin until the prototype is vendored under `docs-site/prototype/`. *Reaction:* prototype intake is a hard precondition; until it lands, only the data-layer, transport-route, gating, and shared-type work (all grounded in verified PD-2 contracts) can proceed — component porting and the `theme.ts` token values are blocked. Forward: tasks — the operator must supply the prototype source location; it is not derivable from the repo.
- **Feature branch HEAD has no daybreak code (research.md §2).** PD-1/PD-2 are on `origin/daybreak-spike` only. *Reaction:* merge `origin/daybreak-spike` (tip `2cbad6ad0e78`) onto the feature branch as the first task; if PD-2 is still WIP there, the open question (proposal) resolves to "reconstitute PD-2 before UI." Routes and types depend on PD-2's `client.ts`/`gate.ts`/`types.ts` existing exactly as cited. Separately, PD-2 task 1.3's `enrich_alert_schema.test.ts` (`alertInputSchema`/`packageEvidence`) is confirmed absent on every `daybreak-spike` ref — a real, unresolved PD-2 gap, not a desync artifact — and is not fixed by this merge.
- **No HTTP API exists (research.md §6, verified).** The proposal's "real data wiring from the plugin's HTTP API" assumes an API that is absent. *Reaction:* PD-4 adds the thin transport routes above. Risk: routes drift from client method signatures; mitigated by making each route a 1:1 wrapper over a single `EvidenceClient`/`ProposalClient` method with no inline logic.
- **PD-3 eval harness does not exist yet (research.md §7).** The feature context records PD-2 still `active` and no registered PD-3 plan, so the `@kbn/evals` primitives FR-9 tells PD-4 to reuse are not produced code. *Reaction:* PD-4's UI-journey eval is sequenced behind PD-3; it blocks rather than building a parallel harness (FR-9 / proposal forbid a parallel harness). If PD-3 has not landed by PD-4's eval task, that task — and the visual-diff screenshot assertion — wait on PD-3, not on UI code. Forward: specs — confirm PD-3→PD-4 ordering, or scope a minimal shared fixture set PD-3 can later absorb.
- **NFR-2's "experimentalFeatures" wording does not match the code (research.md §4).** The only gate is `xpack.daybreak.enabled` (`common/config.ts:17`); there is no `experimentalFeatures` entry, and the plugin registers no app route today. *Reaction:* gate the app on the verified config boolean (the same `this.config.enabled` the server already checks at `server/plugin.ts:33`/`:43`), surfaced to the client via `appUpdater`. Forward: specs — confirm whether the platform also requires a registered `experimentalFeatures` capability for a default-off app, or whether config-gated `appUpdater` suffices; if required, add it without changing the user-facing default-off behavior.
- **Gate fail-closed correctness (FR-7, A-3).** If the UI replicated the gate rule client-side, an under-evidenced proposal could be marked approved locally. *Reaction:* approval is always a server round-trip through `transitionStatus` (`client.ts:34`), which calls `requireReadinessGate` (`client.ts:189` → `gate.ts:98`); the UI never flips local state to `'approved'` until the server returns the transitioned proposal, and on `422` it renders `missingRequirements` (`gate.ts:22`) instead. The UI-journey eval asserts an under-evidenced proposal is rejected (the UI-level echo of A-3's regression-flip).
- **Space-scoped client misuse (NFR-4).** Clients are space-scoped (`evidence/client.ts:56`, `proposals/client.ts:65`); a wrong space resolver leaks cross-space data. *Reaction:* routes resolve the request space from the platform spaces API and construct the client per request; the existing `createSpaceFilter` (`evidence/client.ts:53`, `proposals/client.ts:62`) enforces scoping once the space is correct. The browser never receives an ES client — only the typed route responses (NFR-4: no prompt injection via direct store access).
- **Token→EUI mapping drift.** With the prototype absent, the 1:1 token mapping cannot be confirmed; the visual-diff acceptance gate could fail. *Reaction:* each ported surface is diffed against the prototype before implementation (per the proposal), and the eval captures a dark-theme screenshot assertion for shell + one thread + the brief.
- **Playwright brittleness against live Kibana UI (A-5).** Loading states and async updates can make the UI-journey eval flaky. *Reaction:* explicit wait-for-state assertions (`toBeVisible`, `waitForResponse`), never fixed timeouts — per the PD-4 reconciliation row.
- **Empty stores when the worker hasn't run.** The UI renders worker output; if PD-2's worker hasn't executed, the stores are empty. *Reaction:* the UI-journey eval seeds the stores via the PD-3 golden set or the `create` routes (`evidence/client.ts:28`, `proposals/client.ts:28`) before driving the UI.

## Alternatives Considered

- **Generic Kibana chrome instead of a prototype port.** Rejected: FR-11 and the acceptance gate require prototype fidelity (the visual-diff assertion), and the proposal's design source-of-truth is the prototype, not stock EUI.
- **Mocked data instead of real wiring.** Rejected: FR-11 requires real worker output; the proposal's "Data wiring (not mocked)" is explicit. Mocking would also hide transport-route and gate-wiring defects the eval must catch.
- **Replicate the gate rule client-side for a snappier approval UX.** Rejected: FR-7 and A-3 require fail-closed approval; `transitionStatus` already enforces `requireReadinessGate` server-side (`client.ts:189`), so client-side replication would only introduce a way to bypass it.
- **Expose Elasticsearch to the browser directly.** Rejected on NFR-4: the browser touches only typed route responses; ES access stays server-side behind the clients.
- **Port the full prototype surface set (Discoveries, DeepWatch, Streams, Watches, Workflows, Skills, Activity, Performance, Guardrails, AgentsHub, Hunt, projects, templates).** Rejected: the proposal's non-goals defer these to follow-up plans; PD-4 lands only analyst chat + brief + inspector + gates.
- **Build a parallel eval harness for the UI.** Rejected: FR-9 and the proposal require reusing the PD-3 `@kbn/evals` primitives; a parallel harness would duplicate the gate/fixture infrastructure. (This holds conditional on PD-3 existing — see Failure Modes.)
- **Put the new HTTP routes in a separate plugin.** Rejected per the default-to-in-place principle: the routes are thin transport for daybreak's own stores and belong on the daybreak server, in `start()` alongside the existing `runSpikeWorkflow` wiring (`server/plugin.ts:55-62`).

Forward: tasks — enumerate the per-surface prototype-diff checkpoints (shell, thread, brief, gate) as discrete verification steps, each blocked on prototype intake. Forward: specs — decide whether lifting the shared types to `common/` is a PD-4 change or a coordinated PD-2 amendment, given PD-2 owns those files today.
