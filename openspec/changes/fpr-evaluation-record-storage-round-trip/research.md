# Research: FPR WorkerEvaluationRecord Storage Round-Trip

## Research Question
Do this repository's existing `@kbn/evals` storage APIs support a complete WorkerEvaluationRecord round-trip — write through the real production-facing dataset/experiment write path, read back through the real query/read API, asserting field fidelity and exactly-one-record-per-run semantics — and which existing module should host the serializer/type?

## Summary
The storage substrate the proposal bets on is present, mature, and already exercised by a deterministic real-ES integration test. The production write path is `EvalsClient.ingestScores` → `POST /internal/evals/scores` → `EvaluationScoreService.write` against the `.evaluation-scores` data stream; the production read path is `EvalsClient.getExperimentScores` → `GET /internal/evals/experiments/{id}/scores` → `EvaluationScoreService.search`. Exactly-one-record-per-run is enforced structurally via a deterministic ES `_id` and a `create`+409-conflict write. The field-representability seam is real but narrow: `evaluator.metadata` (ES `flattened`) is the only arbitrary-key, queryable slot, so most semantic WorkerEvaluationRecord fields survive a round-trip only there. The unresolved scoping question is that no FPR/daybreak eval suite or worker/eval module exists in this checkout to host the serializer.

## Detailed Findings

### 1. The production-facing score WRITE path is `ingestScores` → `/internal/evals/scores` → `EvaluationScoreService.write`
The harness's `EvalsClient.ingestScores(request)` POSTs an `IngestScoresRequestBody` to `EVALS_SCORES_URL` (`/internal/evals/scores`) and parses `IngestScoresResponse` (`{ ingested, conflicted, failed }`). The Kibana route handler `registerIngestScoresRoute` validates the body with `IngestScoresRequestBody` and delegates to `evalsContext.evaluationScoreService.write(request.body)`. `EvaluationScoreService.write` converts each score into an `EvaluationScoreDocument` via `toEvaluationScoreDocuments`, then `client.create({ documents, refresh: 'wait_for' })` against the `EvaluationIndices.SCORES` data stream (`.evaluation-scores`). `refresh: 'wait_for'` makes the written document immediately searchable, so the read-back in the same test sees it without sleeps. This is the single, canonical production write path — there is no separate "experiment write" endpoint; experiment identity is carried *inside* the score document, not written ahead of time.

### 2. The production-facing READ/QUERY path is `getExperimentScores` → `/internal/evals/experiments/{id}/scores` → `EvaluationScoreService.search`
`EvalsClient.getExperimentScores(experimentId, { suiteId, taskModelId })` GETs `EVALS_EXPERIMENT_SCORES_URL` and parses `GetEvaluationExperimentScoresResponse` into `EvaluationScoreDocument[]`. The route handler builds a filter via `buildExperimentFilterQuery`: it filters on `experiment_id` by default, or on `metadata.execution_id` when an `execution_id` query param is supplied (optional `suite_id` + `model_id` refinements), calls `evaluationScoreService.search({ query, sort, size: 10000 })`, and returns the raw `_source` of each hit. A second read surface, `EvalsClient.getExperimentStats` (`/internal/evals/experiments/{id}`), returns aggregated `EvaluatorStats` (mean/median/stdDev/min/max/count per dataset+evaluator), not per-record documents. Dataset-level read (`getDatasetByName`, `/internal/evals/datasets/{datasetId}`) and dataset write (`upsertDataset`, `/internal/evals/datasets/_upsert`) are separate and operate on the `.evaluation-datasets` / `.evaluation-dataset-examples` streams — they do not carry run outcomes. So the round-trip the proposal describes (write an evaluation record, read it back) maps to ingest-scores → get-experiment-scores, not to the dataset APIs.

### 3. Exactly-one-record-per-run is structural, not a convention the worker must impose
`computeScoreDocumentId` derives the ES `_id` as `experiment_id - suite_id - task.model.id - example.dataset.id - example.id - evaluator.name - repetition_index` (defaulting `suite_id` to `'unknown-suite'`). The write uses the `create` op, so a second write with the same identity tuple returns HTTP 409, which `write` counts as `conflicted` (not `failed`). Run identity is itself deterministic: `experiment_id = uuidv5(executionId::experimentName::modelId, EXPERIMENT_UUID_NAMESPACE)`; `executionId` derives from `TEST_RUN_ID::modelId` env vars in the harness; `dataset_id = uuidv5(name, DATASET_UUID_NAMESPACE)`. The proposal's "stable capability/run identity" and "exactly-one-record-per-run" requirements are therefore satisfied by passing stable `experiment_id`/`execution_id`/`suite_id`/dataset-name/model values into the existing write path — no new identity scheme is needed, and idempotent re-writes are already the storage default.

### 4. Field representability — `evaluator.metadata` (flattened) is the only arbitrary-key, queryable seam
The stored `EvaluationScoreDocument` has four sub-objects. Their first-class vs. extension capacity, from the Zod schemas and the ES mapping, is:

| Document path | Zod ingest shape | ES mapping | Queryable? | Carries arbitrary keys? |
|---|---|---|---|---|
| `example.input` | `catchall(z.unknown())` | `object, enabled:false` | No (stored only) | Yes |
| `task.output` | `catchall(z.unknown())` | `object, enabled:false` | No (stored only) | Yes |
| `evaluator.metadata` | `catchall(z.unknown())` | `flattened` | Yes (by dotted key) | Yes |
| `evaluator.label` / `.score` / `.explanation` | scalar | keyword / float / text(index:false) | label+score yes | No |
| top-level `metadata` (`ScoreMetadata`) | **strict object** (6 named fields only) | **strict object** mapping | Yes | **No** |

Two consequences for the proposal's required fields:
- **First-class & queryable** (no extension needed): capability/run identity (`experiment_id`, `metadata.execution_id`, `metadata.suite_id`, `evaluator.name`); run-level provenance (`metadata.git`, `metadata.ci`, `metadata.hostname`, `task.model`, `evaluator.model`); dataset version/identity (`example.dataset.id`/`.name`).
- **No first-class field** — representable *only* inside `evaluator.metadata` (flattened, queryable) or as opaque `task.output`/`example.input` (stored, not queryable): worker/profile version, evidence references, Proposal linkage. "Actual outcome" is split: storable verbatim in `task.output` but unqueryable there; its only queryable channels are `evaluator.label` (keyword, ≤256 chars) and `evaluator.score` (float). "Expected outcome / human decision label" can use the dataset's `example.output` (expected ground truth) or `evaluator.label`.

The write path preserves `evaluator.metadata` verbatim (`metadata: score.evaluator.metadata` in `toEvaluationScoreDocuments`), and the canonical integration-test fixture already sets `evaluator.metadata: { source: 'integration-test' }` and reads it back — so a round-trip through `evaluator.metadata` is proven, not hypothetical. This is the concrete shape of the proposal's anticipated contract-seam stop condition (Open Question #2): every required field *can* be persisted, but worker/profile version, evidence references, and Proposal linkage have no dedicated queryable home and must be serialized into `evaluator.metadata`.

### 5. No FPR/daybreak eval suite or worker/eval module exists in this checkout
A repo-wide search finds no `kbn-evals-suite-fpr`, no `kbn-evals-suite-daybreak`, no `daybreak` plugin directory, and no `docs/daybreak-worker-testing-pyramid.md` or `evaluation-trust` docs — those names appear only inside OpenSpec artifacts (PD-2/PD-3/PD-4/PD-5 and this change). The closest in-repo security eval suites are `kbn-evals-suite-security-alert-triage` and `kbn-evals-suite-alerts-rag`. Every `kbn-evals-suite-*` package is Playwright/Scout-based (`playwright.config.ts` + `evals/*.spec.ts`, `src/evaluate.ts` = `base.extend<…>({})`); `kbn-evals-suite-alerts-rag` additionally has a `jest.config.js`, but its `src/evaluate_dataset.test.ts` is a pure unit test of dataset-construction helpers using `jest.fn()` stubs — no suite package contains a storage write/read round-trip test. So the proposal's "existing PD-3 FPR `@kbn/evals` suite" and "existing daybreak worker/eval module" are not present in the main tree; they either live solely in the dedicated spike worktree or PD-3 has not yet produced a committed suite/module. This is the central scoping unknown for "define the serializer in an existing module."

### 6. The integration-test template is the evals plugin's own `evaluation_score_service.test.ts`
The only in-repo example of a deterministic storage write→read round-trip through the real `@kbn/evals` storage path is `x-pack/platform/plugins/shared/evals/server/integration_tests/evaluation_score_service.test.ts`. It stands up a real Elasticsearch via `createTestServers` + `createRootWithCorePlugins`, constructs `EvaluationScoreService` over the real `.evaluation-scores` data stream, calls `.write(getPayload(experimentId))`, then `.search(...)` to read back, and tears down with `deleteDataStream`/`deleteIndexTemplate`. Its `getPayload` fixture is a minimal `IngestScoresRequestBodyInput` with one score (including `evaluator.metadata`) — the model for the proposal's "FPR-shaped record/fixture." `jest.setTimeout(180000)`. This is the harness the new "deterministic integration test" should mirror; notably, it lives in the evals *plugin*'s `integration_tests/`, not in any suite package or worker module.

Confirm the new deterministic integration test should live in the (unconfirmed) daybreak worker/eval module mirroring that harness, or co-locate with the existing evals-plugin integration test. Confirm which the WorkerEvaluationRecord treats as the canonical actual-outcome field for the fidelity assertion. (Forward: design)
